# ROUTE.md - the paste plan (adaptive; the goal is digits per session time)

Copy-and-paste only: five command pastes carry the whole session (P1-P5). Each is one command that runs to the end (every step has a timeout, a failed step still prints its summary, the allocation is held
by `alloc.sh` across pastes) and ends in ONE summary of at most 80 lines that the user pastes back. Scripts: `remote/run/*.sh` (contract in AGENT.md). Machine facts, planner limits, time model, output glossary,
known problems: `FACTS.md`. Paste from the repository root. Times are wall clock without queue waits (permissive queue: expect short ones); "expect" = measured on aac7 or modelled, the target may be slower (FACTS "Measured runs").

| paste | what it runs | expect | go / no-go |
|---|---|---|---|
| P1 | check, facts, allocation, build both paths, gates at 1 and 2 nodes, host memory edge on one node | 30-50 min (the edge probe is the last call: up to 7 min) | s0 manifest clean, s1 PASS (4 GPUs, 8 NICs), s2 both paths built, every gate `VERIFY OK` with the 1e9 hash; `host_edge_gb` / `malloc_edge_gb` printed (information, never a stop) |
| P2 | node screen, 64 nodes at 5.12e11, residue / thread-team and DM_MN_WRAP A/B (three 64-node arms at once, three rounds), then 576 nodes at 4.608e12 twice (round size 128, then 1024) | 40-70 min (screen up to 20, A/B about 8, each 576 run about 6-8) | `VERIFY OK` in every row, no slow hosts, 576 n total within 1.5 x the 2026-10-26 figure (255 s cold; the first 576 run carries two diagnostic switches); the two decision lines printed |
| P3 | the first record run: 1e13 on 576 nodes (staircase step 1) | 5-15 min | `VERIFY OK`, per-APU peak below the edge with its excess over the plan noted |
| P4 | staircase steps 2-4 (2e13, 2.8e13, 3.82e13), stops at the first failure | 20-90 min | each step `VERIFY OK`; the memory rule lets the next step run |
| P5 | `report.sh`: one table of every run, then release of the allocation | 1 min | the agent writes the REPORT (AGENT.md) |

Total 5 pastes when nothing fails, 6-8 with fallbacks. Tell the user the allocation time for P1: (session hours) minus 15 min (`<H:MM:SS>` in P1; the hold must outlast every paste: step 4 needs its `--tmo` + 5 min = 95 min left when it starts, and `stair.sh` skips a step the hold cannot finish and prints the minutes left and the time needed, then `alloc.sh --release` and a new `alloc.sh --nodes 576 --time <H:MM:SS>` for the rest). The measured per-APU excess of a passed step is kept in `site.env`, so P4 starts from P3's excess (the `need` printed per step). A paste whose time exceeds what is left (plus 20 %): Minimal route.

```
cd <repo> && bash remote/run/chain.sh --brief "s0_check.sh" "alloc.sh --nodes 576 --time <H:MM:SS> --wait 0" "s2_build.sh --path both --jobs 32" "alloc.sh --nodes 576 --time <H:MM:SS> --wait 900" "s1_facts.sh" "s3_gate.sh --nodes 1,2 --path both --digits 1e9" "edge.sh"
```

Add `--partition/--account` to both `alloc.sh` calls after an error says which are needed (the s0 lines list the partitions). Not started after the wait: P1 stops at s1 (verdict FAIL, `PENDING` line): re-paste only

of another size is replaced); then every 576 below means the granted count.
Go on if: s0 PASS (manifest clean; python3, make, sbatch, srun, sinfo, squeue, scontrol present (any missing = FAIL); a compiler, `module` and ROCm/SMA/libfabric modules found, salloc optional (any missing = PARTIAL,

the built path, `s3_gate.sh --path both` skips the missing one, every later command uses `--path <built path>`); s1 PASS (`gpu_count` 4, `nics_cxi` 8, `shmem_test_rc` zeros, `site.env` written); every gate `VERIFY OK` with hash
bf9f4b08758b40d9 at 1e9. s1 PARTIAL with `advisory: NICs per node = N`: read FACTS known problems before going on. s0 PARTIAL with `exec_bits=missing`: run the `chmod +x ...` printed in `next=`, then P1 again.

## P2 node screen, residue A/B, and the first 576-node runs at a known size

```
cd <repo> && bash remote/run/stair.sh --path 1 --budget 110 --ab "64|512e9|ECALC_RESIDUE=shoup ECALC_OMP_TEAM=mask|DM_MN_WRAP=0" --step "64|512e9|ECALC_VERBOSE=1 ECALC_FIT_PER_APU=1 MEM_REPORT_DEVS=1|--screen" --step "576|4608e9|ECALC_VERBOSE=1 ECALC_FIT_PER_APU=1 MEM_REPORT_DEVS=1|--round-ab 1024"
```
Step 1 screens every node of the allocation (up to 20 min, `tools/nodescreen.sh`: upload stall, init time, 8 NICs) and runs 64 nodes at 8e9 per node on the good ones. `--ab` then runs three rounds of one `arms.sh` call, three 64-node arms at once on the screened nodes (about 8 min; needs 192 usable nodes, otherwise `ab: not run` and the route goes on): A = the step-1 words (defaults), B = A + `ECALC_RESIDUE=shoup ECALC_OMP_TEAM=mask` (bit-identical by design; the digit residue is per node, so 64 nodes show what 576 would), C = A + `DM_MN_WRAP=0` (at 8e9 per node the automatic rule turns the division wrap ON, so C is the contrast; the planner puts the wrap at 7.64 GB per APU from 2.7e13). The arm order rotates between rounds, so every arm runs on every host block. Each run prints its total, bs/dm/dc and `device_peak_apu_gb` (measured), so the wrap's memory cost (A minus C) and time saving (dm of C minus dm of A) are both measured at the target.
Step 2 is the 4.608e12 run of 2026-10-26 (VERIFY OK, 255 s cold, 111 s of it init) as the reference for the record sizes; `--round-ab 1024` runs it twice on the same hosts, first at `XSHMEM_ROUND_MB=128` (the default, set explicitly), then at 1024, both with
`MN_WAIT_STATS=1 XSHMEM_ROUND_STATS=1` (diagnostics only: clock reads, no digits change; their lines are in the run logs, `show.sh <run dir> grep XSHMEM_ROUND_STATS`). Rows are `1`, `2` (128) and `2b` (1024). Slow hosts are printed (`screen:` line) and left out of the later steps.
Decisions printed by the script itself (the agent copies the lines, does not recompute):
- `ab decision:` (B, residue / team) ADOPT when every run is VERIFY OK with the same last digits, B's dc is below A's smallest dc in every round (beyond the A-A spread of the three A runs) and B's mean total is at most 2 % above A's; the words go to `site.env` as `REMOTE_RECORD_ENV` and every later step (step 2 and P3/P4 in later pastes; each row's `env:` line shows it) carries them. Expected from aac7: dc 14 s to under 1 s per node (the target measured 13.15 s per node at 8e9 with the default team). Digits that differ between runs: FAIL, stop (AGENT.md Failure handling).
- `ab wrap decision:` (C) the wrap's dm saving is RESOLVED only if every C dm is above every A dm (beyond the A-A spread); then the auto rule stays. Not resolved: `REMOTE_WRAP_ENV=DM_MN_WRAP=0` goes to `site.env` and every step of 2.5e13 digits or more (the 2.8e13 calibration and the 3.82e13 record) adds it, so both share one layout (at 3.82e13 the auto rule is off anyway: planner, FACTS). The agent copies the `ab wrap:` line (dm ranges, saving, peak per APU of A and C) into the REPORT.
- `round decision:` ADOPT 1024 when its total is lower by at least 3 % AND bs+dm are lower AND both runs are VERIFY OK with the same last digits; `REMOTE_ROUND_MB=1024` goes to `site.env` and every later step adds `XSHMEM_ROUND_MB=1024` (a step whose own words set it keeps its value). Otherwise 128 stays and `REMOTE_ROUND_MB` is removed. This simple rule is the fallback of the refinement below. Why a test: the fitted model puts most of the target's exposed fabric time into per-round synchronisation, so a bigger round should help at 576 nodes (modelled, `ecalc/mn_model.py estimate --g 576 --fabric target_fit`: 4.608e12 171.8 s at 128 vs 157.2 s at 1024; 8e12 240.9 vs 200.2; 3.82e13 1072 vs 704 s), but the fit cannot tell round sync from latency or bandwidth (assumed mechanism), and at 64 nodes the difference is 2 s, too small to see. Cost of 1024: +3.2 GB device pool per node, which also counts in the host figure (+0.8 GB per APU; FACTS), so each staircase step's margin rule is evaluated with the setting in force. A failed 1024 run (rc, timeout, planner refusal) leaves 128 in force and the paste ends PARTIAL; two runs that both pass VERIFY with different last digits are a FAIL.
- Per-round statistics (nothing can be copied off the target: only these screen lines come back). After each of the two 576 runs the script prints `stats <MB>:` lines and a `round_stats_<MB>=` key: `XSHMEM_ROUND_STATS (final)` aggregated over all PEs (pes, mean and max rounds per PE, phase-1 and signal-wait seconds per PE and per round in us) and the rank-0 `wait-stats max/min over nodes` of each phase (barrier and wait seconds, from `MN_WAIT_STATS`). `no XSHMEM_ROUND_STATS (final) lines` means the build prints none: say so and use the simple rule.
- Refinement for 512 vs 1024 (the browser agent, only when both runs are VERIFY OK with identical digits; arithmetic on the printed numbers, no run): k = (total of run 2 minus total of run 2b, measured) divided by the modelled saving of the same pair (`python3 ecalc/mn_model.py estimate --g 576 --D 8e9 --fabric target_fit --round-mb 128` minus `--round-mb 1024`, the total is column 5 of the 576 row; modelled 14.6 s). The model's per-round synchronisation constant is `ROUND_SYNC` = 1.15e-3 s per round and peer^0.5 (`round_sync_cost` in `ecalc/mn_model.py`; exponent via `MN_MODEL_ROUND_SYNC_EXP`); scale it: `MN_MODEL_ROUND_SYNC=<1.15e-3 x k> python3 ecalc/mn_model.py estimate --g 576 --D 6.632e10 --fabric target_fit --round-mb R` for R = 128, 512, 1024 (3.82e13 = 6.632e10 per node). Choose 512 when its modelled total is within about 1 % of the 1024 total (smaller pool: FACTS gives the per-APU and node figures at 128 / 512 / 1024), else 1024 if it clears the simple rule, else 128; k near 0 or negative = round size does not matter here: keep 128. Cross-check k with the stats: the rounds per PE of run 2 over run 2b should be near the ratio the model uses (rounds = chunks x ceil(bytes / chunks / R MB)); a mean signal wait per round far from the model's per-round cost says the assumed mechanism is wrong, report it. A 512 choice is written by hand as `XSHMEM_ROUND_MB=512` in the words of the P3/P4 steps (the step's own words win over `REMOTE_ROUND_MB`).
Go on if: every row `VERIFY OK`; `slow_hosts` empty; the 2 / 2b totals below 1.5 x 255 s (the unexplained init growth at 576 nodes is a known anomaly, FACTS; init alone does not stop the route). The model grows 14 % from 8 to 64 nodes and
24 % from 64 to 576 (ADJUST.md section 1): a step far above that is fabric, launch or placement trouble.
Fallbacks: `slow_hosts` listed: no spare node exists at 576 (the machine has 576), so step 2 stops with `only M usable nodes` or `fewer than N nodes remain`: take "Fewer than 576 usable nodes" below. 64-node step fails for
placement reasons: re-paste only the 576 step once (the `--ab` option needs step 1 and is dropped with it; `--round-ab` works alone). `rc` 8/9 or `plan REFUSED`: the printed largest fitting digits, or `MN_T_CHUNK_MB=1024`; rc 124 (timeout): `show.sh latest tail 40` and the registration setting in FACTS;
a digit mismatch is never moved past (AGENT.md Failure handling). Optional extras of the old tuning stage (path A/B, collectives) are in the appendix; use them only when the user asks.

## Record-size output (`--write` on step 4; also 2e13 and 2.8e13 if the user wants files)

Sizes (packed v2 = 0.41667 B per digit + a 4096 B header per part): 2e13 = 8.3 TB, 2.8e13 = 11.7 TB, 3.82e13 = 15.9 TB. Path 1 (layout D) writes 576 part files `<out>.part<k>` of 27.6 GB each; one writer thread per part: O_DIRECT,
256 MB chunks over 8 `pwrite` threads, started at the division's hook (`MN_OUT_EARLY=1`), so most of the write hides behind the low product; the exposed part is in the `wrote <file>.partNNNN` line. The target has 1.7 PB free, no quota (FACTS Target site).
The stripe layout stays `default` (the directory's PFL layout): a different layout needs a measurement of 576 files that no run has made (appendix, IO benches); a write measured at 1-2 nodes ran 3.4-5.3 GB/s per part (single OST).
Modelled write time 6-60 s for 15.9 TB at 0.25-2.9 TB/s aggregate (assumed rates; exposed time smaller); plan the step at the model + 60 s. If the write fails after the compute finished, the run's VERIFY still counts as the result and the
digit file is the missing part: report it, do not re-run the step for the file unless time is left (then re-run at the best size with `--write`). The digit hash is skipped above 300 GB (`TGT_HASH_MAX_GB`); the run's own VERIFY (T1/T2 windows, written by the writer) is the check.

Rules from them: io01 32 threads at least 1.3 x of 8 -> `MN_OUT_THREADS=32`; io03 an explicit stripe arm at least 15 % faster in aggregate than `default` -> `lfs setstripe -c <C> -S <S>M <dir>` before the run (or `MN_OUT_STRIPE=<C>:<S>:<OSTs>`, needs `lfs` on the compute nodes); io02 below 0.5 GB/s per node: tell the user before step 4 writes.

Script features: `arms.sh --nodes N --digits D --path P --arm "NAME:K=V ..." --arm ...` runs K arms of N nodes at once in one allocation (one table: arm, nodes, rc, total_s, init_s, verify, last digits, settings; `--cmd` = per-arm shell command for allocations without NICs; `--dry-run` prints the plan); needs N x arms usable nodes and its times are for screening. `arms.sh` also prints a `bs/dm/dc_s` column and one `arm_<name>=` key line per arm. `stair.sh --ab "N|D|WORDS"` (after step 1, four arms A B B A) and `--round-ab MB` (in a step's EXTRA: the step twice, 128 then MB) are the P2 decision tests above; `edge.sh` is the P1 memory-edge probe. `s5_run.sh`, `s4_ab.sh` and `stair.sh` print per run `layout`, `init_split`, `shifts`, `p24_check` and `device_peak_apu_gb` lines (NA when ecalc did not print them).
