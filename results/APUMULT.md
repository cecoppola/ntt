## Topic summary

apumult is a host-resident reference multiplier/e pipeline (spec "a37v1") that reached 2.35e11 digits per node (475 GB, SSD spill, madvise) but is 3.2-3.7x slower per digit than ecalc at 4e10 (234.8 s against 63.5-73.1 s (m)). Its doc claimed that porting its spill/madvise stack would lift ecalc's 576-node target from 4.0e13 to about 1.3e14 digits. The study checked every apumult technique against ecalc `main` of that date and measured the disk and memory behaviour of the APU. Conclusions that still hold:

- **ecalc already has (or beats) nearly every a37v1 technique**: same four RNS primes, batch tier with all primes on the owning APU, fused pointwise/L^-1/Garner+carry, no bit reversal, correction-form anchored Newton, band-cut products, view-based arena. ecalc's 2^31 forward NTT is 99-100 ms (m, `results/KERNELS.md §K13b`) against 144 ms; one-node 4e10 is 63.5 +- 1.5 s (m) against 80.6 s. Of 139 rows about 80 are the same or equivalent and 14 ecalc is ahead.
- **The "3.4x digits" headline does not transfer.** Memory is device-resident with one arena per APU mapped at init and sized by `dm_layout`; `db_free` returns bytes only to the pool, there is no madvise on hipMalloc memory (EINVAL on a PFNMAP VMA), and the node peak is a mapped capacity. A buffer lowers the ceiling only by shrinking `dm_layout`'s formula. Modelled one-node ceilings: 1.30e11 now, 1.68e11 with a P spill plus tail policy (V2), 1.70e11 with V3 (+Q spill, late r2) at the 2^31 cap (2^30: 1.44 -> 1.79 / 1.88e11): +30 %, not 3.4x; apumult's 2.02 B/digit is below ecalc's V3 floor of about 2.3 B/digit. At 576 nodes spilling buys only +5 % (the tree top level, 294 GB, binds next); the built chunking switch (`MN_T_CHUNK_MB=1024`, off) is cheaper (5.32e13 mod). The apumult doc's claims about ntt/ were mostly stale or wrong (list under apumult_F1).
- **What was adopted from the study (current code, see `ecalc/README.md`)**: `DM_TIGHT` (tight reciprocal reservation, per-pair release in the device tier's top levels; was F2 item 1, "E2"), `DM_TAIL_DEAD` (tail re-laid over dead inputs, F1's tail policy), `DB_POOL_VMM` (HIP VMM arena; also removes the contiguity/fragmentation failure), `BS_SEED_FILL`, `BS_BATCH_PIPE` (default 1 since D20; was A37CMP R5, `results/KERNELS.md §N3`). Not adopted: any SSD spill of P/Q/mu (only the checkpoint writer `ECALC_CKPT_TOP`, off by default), the OOM-killing watchdog, madvise, Karatsuba over the device grid (idea only, a time-for-memory trade), FWD_FUSE, "P20" 3-prime pack, base 10^19.
- **Rejected on principle**: skipping the remainder check (T1 residue verification is the only verifier at 3.7e13 digits), Stirling-balanced leaves (a node's term range spans < 3 %), global base 10^19, XNACK=1 (2x slower, RESULTS §55), CPU school tier, arenas on two dies.
- **Disk/APU facts (apumult_M, apumult_R)** that any future spill needs: the page cache lives in the same HBM; use O_DIRECT through a pinned hipHostMalloc bounce ring (O_DIRECT from a hipMalloc pointer fails with EFAULT); `hipMemGetInfo` is useless as a free gauge (use /proc/meminfo); overcommitting hipMalloc OOM-kills the process; madvise(DONTNEED) on host memory frees HBM for hipMalloc immediately; true out-of-core multiplication is hopeless (SSD/HBM bandwidth 1/2000-1/7000 against y-cruncher's needed 1/4).
- **Superseded/stale items**: the apumult summary's table of ecalc numbers (7e10 d_max, 73.1 s, 6.3 B/digit, 121.5 GB pool) is superseded by the F1 section 7 check; F2's per-doubling "used-at-peak" fractions were assumed and are covered by the later `DM_TIGHT` measurements (results/DIVISION.md); A37CMP R1 (GPU seed) is an open candidate, not adopted (check `results/INDEX.md` for the seed items before starting it).

## A37CMP: apumult a37v1 spec against ecalc, item by item

Read-only comparison of the a37v1 spec against ecalc `main` @ 6e220db. Sources include `results/TIME_MODEL.md §S19B`, `results/KERNELS.md §K13b`, `results/TARGET.md §TGTBENCH2`. The spec has no §17; §5/§6 are one line each.

**Five-sentence comparison.**
1. ecalc has almost every a37v1 technique, often better (identical primes `modarith.h:76`, per-APU batch tier, fused pointwise/L^-1/Garner+carry+P-add, anchored correction-form Newton, band-cut/mid/high products, view-based ping-pong arena, seed overlapped with the mapping).
2. ecalc's NTT is faster: 2^31 forward 99-100 ms (m, K13b) against 144 ms; modmul 1.31-1.34 Tmm/s (m, RESULTS §19/§31) against 0.94 in-NTT; register-blocked b16 and b1 (1.2-1.33x), bottom-up plans, 3*2^k lengths. a37v1's batch tier (21.0 s at 4e10, ntt 73 %, crt 23 %) is not better than ecalc's (scatter 1.1 + ntt 15.7 + crt 2.6 + merge 0.8 s at 4e10 (m)).
3. ecalc one-node 4e10 is 63.5 +- 1.5 s (m) against 80.6 s. At 10-576 nodes the wall is the fabric (S19B: exchange 79 % of the modelled 576 wall), so single-node kernel ideas touch only init + leaf (about 61 s of 465 s at 10 nodes, 61 of 222-266 s at 576 (mod)).
4. The most useful new fact is the seed: a37v1's GPU seed kernel does 4.35e9 terms in 6 s (spec) against a CPU seed of 25.9 s; ecalc dropped GPU seeds (TASKS 6.4 / E8) because aac7 mapping masked them. On the target mapping is 7x faster (MAP_RATE 0.010 s/GB (m), TGTBENCH2) and the model says seeds bind (init 20.6 + seed wait 9.3 = 29.9 s at 576, S18TGT). a37v1's GPU-seed pitfalls (copyout +9 s, pregrow exposed +10 s) do not apply to ecalc.
5. Two big a37v1 choices rejected: skipping the remainder check and Stirling-balanced leaves.

**Row verdicts (139 rows; only non-trivial ones listed, all others SAME / EQUIV / N/A).**
- Algorithm and representation (rows 1-15): same Taylor/binary splitting; division DIFF (DKM two halves, half-length reciprocal, -25.7 s at 1e11 (m, RESULTS §92)); verification stronger (T1 on 8 primes + T2). Base 10^19 (row 6-7): 3-prime products would allow +5.6 % digits per point (P20 pack, batch levels L <= 2^22, <= 1.5-2 s at 6.4e10 (mod)), but whole-code change; not recommended. ecalc has 3*2^44 | p-1 (superset), 3 primes up to 5.84e10 coefficient terms, P24 (24 digits/pt at 4 primes).
- Flow/arena (16-36): A never formed (10dP: S=P+Q in place); `BS_SEED_FILL=128` picks the span S (about 229-239) so the last span has <= 128 limbs (bs -21 s with BI_MUL1_FAST, RESULTS §86); dm/tree need binds the arena, not bs; four per-APU region arenas (remote HBM read 93 GB/s against 3.8 TB/s local (m)); VMM arena mapped in background (KFD serializes); school tier absent (loss 42-59 s (m), RESULTS §58); P,Q stay on device (no copyout). Open: row 28 seed stream handoff (Q2), row 29 base-2^64 sub-range seed (ecalc's decimal span step 2.6 ns/limb against binary 0.82; a37v1's leaf costs 201 us per 352 terms, so not evidence it beats ecalc).
- Tiers/NTT (37-68): batch tier SAME. Gaps: row 42 batch pipe (one stream per die, a host sync per tile; <= about 2 s at 6.4e10 (mod); later built as `BS_BATCH_PIPE`), row 40 pageable `hd[]` descriptors (<= 1 s), row 50 FWD_FUSE absent (about 10-15 % of the first forward at 2^31 (mod); <= 1 s at 576), row 58 twiddle seed (check once, Q4), row 63 no NOP-modmul breakdown (Q4), row 66 FMA contraction not confirmed in ISA (Q5). ecalc ahead: pass plan {b1 on 2^12 + 3 b16}, register-blocked b16/b1, modmul `NTT_MODMUL=1` (rint == floor in ecalc: 1328 vs 1331 Gmm/s (m)), CRT 2.6 s against about 4.8 s.
- Newton (69-79): all SAME/EQUIV except row 77 skip remainder check (rejected, R1) and row 79 early reciprocal chain: ecalc's chain to 34126 limbs takes 2.28 s minimum, 6.8-22.2 s typical (15 runs, mean 12.4 s (m, S19B §2)).
- Output/memory (80-83): row 80 `fmt18` peels 18 digits with %10 and /10 (`DC_FMT_MN` 0.061 s per 1e9 digits (m) = 5.8 ns/digit-core; S19B `dc` 2.8-4.1 s at 6.44e10); a37v1 formats 4e10 in 0.5 s; unsure whether `dc` is formatting, D2H or T1 residues. Memory 363.5 GB device / 405.6 GB node at 6.44e10 (mod, S18TGT), 5.6 B/digit.
- Flags (84-118): all analogues listed; `HSA_XNACK=1` is the opposite of ecalc (XNACK off; 1e10 80 -> 159 s with it (m, RESULTS §55)); `NTT_REGBLOCK=0` is a different technique under the same name.
- Pitfalls (121-128): SDMA + migratable SVM hang N/A with XNACK off (TASKS B7/H5 would be a risk if combined); hipHostRegister of fresh anon-mmap + concurrent GPU write gave 1/18 corruption in a37v1, ecalc pretouches (`mem.c`, `comm_ofi.c`) but **not verified** for `comm_shmem.c:318` (`S.pool` from `shmem_malloc`); `kill -KILL` of large GPU jobs poisons KFD: `rundriver.sh` uses SIGTERM + 60 s grace, `a14_soak.sh` and `g13d_hang.sh` still kill -KILL.
- Tests/"don't" items (129-139): ecalc stronger; GPU-seed warning does not transfer.

## apumult_F1 — categories A and D, ranked ports and architecture against ntt/

Question: what do apumult's SSD spill/stream and trim items give a device-resident ecalc, and what must change to port them? Labels: measured (aac6 runs), modelled (`mem_model.py`, equal to the C layout to the byte and to measured device totals within 0.05 %, M13), assumed. No code changed. Integrator note: apumult's numbers were taken on the target's own MI300A nodes with a node-local `/ssd0`.

**The one fact: what sets the one-node peak.** Device memory is mapped at init: planes (103.7 GB at cap 2^31, 60.7 at 2^30 (m, P13b)) + one arena per APU = max(bs regions, dm need) + 0.6 GB tables, beside 12-17 GB host HWM. Above about 5e10 digits the arena is the dm need, the larger of two `dm_layout` terms (B = bytes of Q, 0.444 B/digit): **v2** (reciprocal peak: Q + S + r + r2 + t1 + one grid piece + slack) about 6.2 B + piece; **v3** (bs top level beside the tail: 2P + 2Q inputs, P,Q outputs, +1/8, + the reserved hole of t1's 2 B) about 6.95 B. At 1e11: v2 = 298, v3 = 310 GB binds (mod = measured 431/414 within 0.1 %); node 428 GB. The measured edge is device + host HWM <= 524 GB (P13b), so ceilings 1.30e11 (2^31) and 1.44e11 (2^30) (m). Consequences: (1) a cold buffer frees bytes only if `dm_layout` is shrunk by it (spill + `db_free` + smaller formula + restore, never a spill alone); (2) spilling P alone gives 0 because v3 binds; the hole policy must change too; (3) at 576 nodes the tree top level (294 GB per node at 7.38e10 against dm need 309) binds next.

**Variants (each includes the previous; changes to `dm_layout` plus spill code).** V0 today; V1 P spilled under the reciprocal (v2 5.1 B + piece); V2 = V1 + tail policy (t1's block = the parity half that held the top level's dead inputs, no hole; v3 4.95 B); V3 = V2 + r2 reserved after the first product, Q spilled from the last iteration's second product through the high product, window formed and S freed before the low product (v2 about 4.2 B + piece); V4 = bs top level frees each input as consumed (about 4.33 B); V5 = + fresh Q and P2 spilled during T = P1 Q2 (apumult M56, about 2.5 B).

| 2^30 | 1.443e11 (m 1.44, 1.46 OOM) | no change | **1.794e11** | **1.882e11** | no change |

Traffic 2 x Q: 150 GB at 1.7e11 = 150 / 75 / 50 s at 1 / 2 / 3 GB/s. Verdict: test as part of V3.
- A2 `DM_P_SPILL` (M32): same dead interval as ours (`bs_Pd` until `db_add(&bs_Pd,&bs_Qd)`); the write half already exists (`ECALC_CKPT_TOP` + `bs_ckpt_bg_*`); missing: `db_free` after the writer's P part, read-back, smaller arena. P = 1.1 B = 49 GB at 1e11. Alone 0; with the tail policy **1.31 -> 1.68e11 (2^31), 1.44 -> 1.79e11 (2^30)** (mod). **Architecture note.** Right: device -> pinned bounce -> SSD. ## apumult_R: spilling to SSD and releasing memory on MI300A (research findings)

Agent R, 2026-09-24; web sources plus Linux v6.8 kernel source (amdgpu/TTM/mm); no GPU available, so items marked "verify" have 1-minute tests (end of section). Confidence: **H** documented or read in kernel source, **M** strong inference, **L** plausible.

**Answers in brief.** (a) Spilling without the page cache taking HBM: yes with O_DIRECT (or `RWF_DONTCACHE`, kernel >= 6.14; aac6 runs 6.8); buffered I/O puts the cache in the same HBM and 2 MiB hipMalloc will not reclaim it (falls back to smaller pages); `fadvise(DONTNEED)` drops only clean pages (H). (b) Bandwidth: aac6's 970 EVO Plus (as then assumed; agent M later found a 980 PRO, m 2.0 / 5.9 GB/s) about 3.3 GB/s write for the first about 78 GB then 1.5-1.75 (0.8 on the "Elpis" revision), read 3.3-3.5; target (EX255a-class, one optional M.2 per node, PCIe Gen4) expect 2-4 write, 5-7 read GB/s (L-M); measure `/ssd0` with fio. (c) HIP VMM release of dead device pages: works (`hipMemUnmap` + `hipMemRelease`), cost about 35-40 ms/GiB for kernel zeroing when re-created (M), still Beta with open gfx94x issues; chunked hipMalloc/hipFree gives the same saving without it; `madvise` on a hipMalloc pointer returns EINVAL (H).

**MI300A memory model.** `hipMalloc` is a TTM GTT buffer object of ordinary system pages (no VRAM on an APU), counted against the TTM limit (96 GiB-of-128 default; raised with `amdttm pages_limit`); about 37 ms/GiB to allocate, best contiguity and 3.5-3.6 TB/s (H). `hipHostMalloc` 200-400 ms/GiB, 2.1-2.2 TB/s in the literature; our own measurement: 460 GiB through it passes the TTM cap at 14.0 TB/s per node (M: a USERPTR/SVM mapping of anonymous pages). `hipMallocManaged` up front with XNACK off, first touch with XNACK on. `malloc` needs XNACK for GPU access (about 18 us per fault, up to about 1.1 M pages/s; about 15 % penalty with 4 KiB pages unless THP). AMD requires `transparent_hugepage=always` and proactive compaction on MI300A.

madvise(DONTNEED): on malloc/mmap anonymous memory returns pages to the buddy allocator that hipMalloc's TTM pool draws from (release whole 2 MiB ranges; do not use MADV_FREE) (H); on a hipMalloc pointer EINVAL (`VM_PFNMAP|VM_IO` forbidden, H); on hipHostMalloc not recommended (L). Trap: freed hipMalloc pages go to the TTM pool, which clears them and keeps up to `page_pool_size`, so MemFree stays low after `hipFree`; an RSS/MemFree watchdog (apumult's pollv3) misreads it. Page cache: no DDR, so on El Capitan-class systems `/tmp` is a RAM disk in HBM (never spill to /tmp); TTM tries order-9 pages with no direct reclaim, so a node full of page cache yields fragmented 4-64 KiB hipMalloc pieces and slower kernels (H code, M effect; our own note: a run after a 40 GB digit comparison was 5-15 % slower until the file was evicted). Avoid with O_DIRECT (4 KiB-aligned, ideally 1-8 MiB I/Os), or `sync_file_range`/`fdatasync` then `fadvise`, or `RWF_DONTCACHE`.

**HIP VMM.** API: `hipMemCreate`, `hipMemAddressReserve`, `hipMemMap`, `hipMemSetAccess`, `hipMemUnmap`, `hipMemRelease`; Beta since ROCm 5.x/6.0. Known issues: intermittent "hipMemCreate out of memory" for 64-128 MiB on gfx94x CI; ROCm 7.14 opens one fd per hipMemCreate (false OOM at about 1017 handles with `ulimit -n 1024`); release does not synchronise the device. Granularity 2 MiB physical (reported values vary by version). Release/restore pattern: reserve a large VA, back with chunk handles (256 MiB-1 GiB), unmap+release to free, create+map+setaccess at the same VA to restore; putting back 100 GiB costs about 4 s (M); VMM memory still counts against `pages_limit`; cheaper equivalent: K separate hipMalloc chunks with a pointer table. VMM memory cannot be an O_DIRECT target.

**Moving device data to NVMe.** O_DIRECT into a hipMalloc pointer fails with EFAULT (H code; agent M confirmed (m)); a buffered write works but fills the page cache; O_DIRECT from hipHostMalloc/posix_memalign memory works (zero-copy spill if the buffer lives there; M). Use a bounce ring of 2-4 pinned 64-256 MiB buffers (HBM to HBM copy 58-90 GB/s by SDMA, at least 20x faster than the SSD, so the bounce is free); dbig's 1.6-2 GB/s is disk-limited. 2-4 threads with 1-8 MiB O_DIRECT or io_uring depth 8-32 saturate one NVMe. hipFile ("AMD Infinity Storage") is an early-access preview (needs ROCm >= 7.2, `CONFIG_PCI_P2PDMA`); on MI300A it buys nothing beyond O_DIRECT from hipHostMalloc memory (M).

**y-cruncher Swap Mode lessons.** True out-of-core with raw I/O; storage needs about 1/4 of memory bandwidth (diminishing above 1/3); the 100 T pi run wrote about 350 bytes per digit (31.5 PiB written, 35.7 PiB read). e records: 35 T digits (2023-12-24, 512 GB RAM, 94.5 h compute + 92.5 h verify), 12 T (2020, 252 GB, 25 hard drives, 19.4 days), 1 T (2010, 12 GB, 8 x 1 TB, 224 h). Our ratio SSD 2-7 GB/s against HBM about 14 TB/s is 1/2000-1/7000, so true out-of-core multiplication is hopeless; only "park dead-until-later buffers" spilling at phase boundaries is viable (cost = bytes/BW_w + bytes/BW_r, partly overlappable); choose candidates by bytes freed / seconds of I/O not hidden; use raw I/O, checksums, one file per buffer on local XFS/ext4 (M).

**Node-local storage.** HPE Cray EX255a: optional 1 local NVMe M.2 per node (PCIe Gen4); model and bandwidth unknown (L), a Gen4 enterprise drive is typically 5-7 GB/s read and 2-4 sustained write; the target's `/ssd0` is presumably this drive. El Capitan class: no local SSD on compute blades, shared Rabbit flash (about 200 GB per node `/l/ssd` default, XFS, wiped at job end); Lustre about 0.23 GB/s per node when all write; other MI300A sites vary. At 576 nodes node-local M.2 is optional hardware, Lustre is not a spill target; confirm device, capacity and fio numbers before planning d_max (at 1.35e14 the spill volume per node is several hundred GB).

**Samsung 970 EVO Plus 2 TB (as assumed for aac6).** PCIe 3.0 x4, 3.5 / 3.3 GB/s spec, 1200 TBW, SLC cache about 78 GB then about 1.5-1.75 GB/s; post-2021 "Elpis" units have a 3x larger cache but about 0.8 GB/s sustained and run hotter (check `nvme id-ctrl`). 200 GB spill: write about 105 s (Phoenix), read about 60 s, round trip about 165 s (Elpis estimate 210-310 s); the cache refills only when idle; endurance 2400-6000 runs at 0.2-0.5 TB per run (not a concern); keep below 80 % full. aac6 caveat: `/` was XFS on an md device, 800 G partition, about 293 G free, so capacity may be well under the drive size.

**Implications.** (a) Spill rules: O_DIRECT for every write and read-back (never buffered, never `/tmp`); pinned hipHostMalloc bounce ring (hipMalloc pointer cannot be the O_DIRECT buffer); buffered output followed by `fdatasync` + `fadvise(DONTNEED)`; release device memory by `hipFree` of chunks or VMM, not madvise; watchdogs must count TTM-pool pages as reclaimable. (b) aac6 about 165 s per 200 GB round trip, not hideable behind a 112 s run at 4e10: test correctness there, not performance; target likely 50-100 s per 200 GB (L). apumult's own figures fit: 3.4x digits at 3.2x slower at 4e10 (234.8 against 73.1 s). (c) Release is cheap; the expensive part is the SSD round trip. Recommendation: chunked device allocations behind the block pool; VMM only if a flat contiguous VA is needed.

**Tests to run on aac6 (1 minute each; several were later covered by agent M or the VMM probe).** VMM support and granularity attributes plus a 64 x 1 GiB create/map/unmap timing; O_DIRECT pread into hipMalloc (EFAULT expected) / hipHostMalloc / posix_memalign; madvise on a hipMalloc pointer (EINVAL expected); fio write/read bandwidth curve with `nvme id-ctrl` (repeat on `/ssd0`); page-cache effect on an NTT pass after a 100 GB buffered write, with and without `fadvise(DONTNEED)`.
