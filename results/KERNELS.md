## Topic summary

Single-node GPU and host kernels of the e-digit run, from the NTT constants (Phase 13) to the dbig add/sub family (October). Current state (checked against `ecalc/README.md`, RESULTS.md, and the code):

- **Adopted and now built in (their switches are gone from the code or README)**: K13 `NTT_MODMUL=1` (reduced-correction Barrett, exact, +5-12 % per transform); K13b `NTT_B1R=3` register-blocked b1 pass and `NTT_PLAN=1` (auto plan that moves the passes off the slow strides, +4-13 % per transform, -4.0 % compute at 4e10); S38/S40/S41 `DBIG_ADDSUB2`, `DBIG_MAXIDX_TOP`, `DBIG_QSEL` (user rule, 2026-10-10: -12.3 s, -1.6..-3.2 s, -0.9..-2.1 s at 1 node; -50 s at 4 nodes); S51 K2 `DBIG_ADDSUB3` and K3 `DBIG_MODQ_MONT` (built in; 1 node -2.03 s +- 1.38 on aac7); G515 `DIST_TWREC_G` (default since 2026-09-28, built in 2026-10-12); S115 `BI_MUL1_FAST` (decimal `mul_1` and fused span step, built in).
- **Defaults on by decision, switch still a fallback** (`ecalc/README.md`): `RNS_CRT_SCAN` (K4b, default 1 since 2026-10-12, D21), `P24_CRT_SCAN` (K4c, default 1 since 2026-10-13, D24), `BS_BATCH_PIPE` (N3, default 1 since 2026-10-12, D20).
- **Dropped (measured)**: K13 H2 MALL-chunked passes (`NTT_MALL`), H7 non-temporal stores, H6 occupancy variants (`NTT_B16_VAR`), `NTT_MODMUL=2` Shoup (loses 4-13 %), `NTT_B1R=4` (dominated by 3); S51 K4 `RNS_CRT_SUB` (no gain); S39 candidate A "raw-once k_gather" (S40 refuted the remote-bound assumption); NTT3P 3-pass 2^31 NTT (design study; its microbenchmark E0 failed the gate, `results/SESSIONS.md §S22 / S23 / S24`).
- **Live conclusions**: (1) the NTT passes are issue/latency-bound at 1.2-1.6 TB/s, not bandwidth-bound; there is no MALL cliff; (2) a stride penalty at s_lo 17 and 24 (about 12 % of a 2^31 transform) is an address-pattern effect that padding or rotation does not fix, so the plan avoids those strides; (3) by-value kernel argument structs with a runtime quarter index cost 112 B/lane of scratch and about 30 % of k_gather: use scalar-select (QSEL); (4) multi-node gains of the dbig kernels exceed the 1-node gains because the same kernels run inside the multi-node division; (5) gains below about 1 s per run are inside run-to-run noise (sd 1-2 s at 1 node); trust kernel-level stats (`DBIG_S51_STATS`) for them.
- **Open**: the k_gather strided write (next floor after QSEL), the k_addsub2 residue (about 1-1.5 s, weak model), k_modq beyond Montgomery, the s_lo 17 mechanism (HBM address hashing suspected), the four-prime `ec_words_to_dec4` (dominates k_crt24 and the four-prime k_crt_batch), K3 never exercised at 4e9 on CPX (modq counter 0), the level-1 host gap of N3 (about 2.3 s).
- **Superseded**: S38's "armed" ABBA (replaced by the 4-node confirmation inside S38); S39's raw-once gather plan (S40); S44's CPX figures are coverage only (CPX XCD devices share one APU's HBM).

## K4b — `k_crt_batch`: the per-chunk carry chain as a parallel carry-lookahead

**Question.** Does resolving the CRT kernel's per-chunk carry chain in parallel (instead of a 256-step serial loop by one thread) shorten the 1-node run at 6.441e10 digits? Baseline: `k_crt_batch` takes 4.5-4.8 s per APU at 1 node (m, `archive:results_merged_2026-10-24/KERNELS.md §S39` row 3).

**Change.** Branch `k4b`, switch `RNS_CRT_SCAN` (0 serial; 1 parallel), files `ecalc/rns_mul.c`, `rns_int.h` (`struct gconst` field `scan`), new test `tests/t_crtk.c`. Per chunk of 256 coefficients, thread j forms w_j = V_j + CY_{j-1} (<= B + 4); the serial overflow o_j = gen_j | (prop_j & o_{j-1}), gen = w >= B, prop = w = B - 1; two wave ballots give the masks, every thread adds A + G (A = gen | prop, G = gen) over 256 bits and reads its carry-in as bit j of (A + G) ^ A ^ G. Barriers per chunk: 3 instead of 5. Serial path is the reference (`t_crtk` compares every limb and spill word).

**Results (m).** `t_crtk 29`/`27` equivalence: 48 cases (3 and 4 primes), all identical. Kernel, C form 2^29 / 65536 stripes: three primes **30.18 -> 13.65 ms (2.21x, 569 -> 1259 GB/s)**; four primes 49.85 -> 34.11 ms (1.46x); 2^27 / 16384: 8.02 -> 3.95 ms (2.03x) / 12.54 -> 8.56 ms (1.47x). Gates (2 n and 1 n, off and on; before the rebase and after two rebases on main, the last with P24 for every multi-node product): all PASS, VERIFY OK, digits identical, segv 0; `t_mul 20` 169 checks and `t_strategy 24 2 V` 12 checks OK both arms. **ABBA 1 node, 6.441e10, 4 rounds (16 runs, all VERIFY OK): B - A = -2.52 s, 95 % CI [-4.19, -0.85]** (per round -3.6, -1.4, -3.2, -1.9 s; p < 0.05); arm means A 71.47 s, B 68.95 s (-3.5 %). Modelled 2.4-2.6 s of kernel time per APU (4.5-4.8 s at 2.21x).

**Verdict.** Adopt candidate, above the 2.0 s assumed in OPPORTUNITIES; merged switch off, then adopted as default 1 (D21, 2026-10-12, `ecalc/README.md`). **Open**: the four-prime form gains less (1.46x) because it is bound by `ec_words_to_dec4`'s sixteen divisions, not by the chain (a cheaper four-word-to-decimal conversion is the next step); multi-node timing not measured here (2-node gates show digits only); `k_crt24` has the same chain (done in K4c). Driver `archive:drivers/k4b/`.

## K4c — `k_crt24`: the P24 CRT's per-chunk carry chain as a parallel carry-lookahead

**Question.** Does K4b's carry-lookahead applied to `k_crt24` (`ecalc/p24_crt.c`, the form of every multi-node product since D18, `results/LAUNCH_DEFAULTS.md §DEF`) shorten the 2-node run at 6.441e10 digits per node?

**Change.** Branch `k4c`, new switch `P24_CRT_SCAN` (0 serial; 1 parallel), files `p24_crt.c` (`k_crt24`, `p24_crt_launch`), new test `tests/t_crt24k.c`. A new switch rather than `RNS_CRT_SCAN` (which had become default by D21 on 1-node data while this branch was open). A chunk of 256 points covers up to 342 limbs (each sums at most three points, quotient CY <= 2, carry-in <= 3, w_i <= B + 2); each thread owns limbs t and t + 256; four wave ballots give the masks of 512 limbs; same barrier count (5), the 342-step one-thread loop is gone.

**Results (m).** `t_crt24k`: 279 checks (9 shapes x 6 coefficient kinds x up to 3 ranks) all identical; `t_p24` against the GMP model 78594 checks OK both switches. Kernel at 2^30 points per rank (rows 4096 / 8192 / 16384): **157.96 / 158.39 / 158.76 -> 101.95 / 101.95 / 101.26 ms, 1.55-1.57x (290 -> 450 GB/s)**. Gates on two commits (2 n and 1 n off/on): PASS x4 each, P24 in use at 2 n. Profiling round: node 0 `crt` sum per run A 4.13 / 4.25 s -> B 2.95 / 2.94 s: **-1.24 s per run** (m, 1 round). **ABBA 2 nodes, 6.441e10/node, 4 rounds (16 runs, VERIFY OK): total B - A = -1.89 s, 95 % CI [-7.51, +3.73]** (per round -2.8, +2.0, -6.3, -0.5; not significant); A 126.28 s, B 124.39 s; dm -0.55 s [-3.00, +1.90], bs -0.43 s [-1.67, +0.82]. Modelled kernel saving -1.49 s per run (4.19 s CRT time at 1.55x).

**Verdict.** The kernel gain is clear, the wall claim unresolved (the A arm had two slow runs, 131.0 and 131.4 s, against B 122.7-125.9 s; resolving -1.2 s at a 3.5 s per-round spread needs about 40 rounds (mod)). Merged switch off, then adopted as default 1 on the kernel evidence (D24, 2026-10-13). **Open**: `ec_words_to_dec4` now dominates the kernel (K4d); the CRT share at larger node counts is not measured (per-node CRT time stays about the same, mod). Drivers `archive:drivers/k4c/`.

## S38: the next single-node speed lever. Found: the dbig add/sub kernel (k_addsub) ran at 36-84 GB/s; DBIG_ADDSUB2=1 (coalesced) cuts 10.4 -> 2.0 s of GPU time per APU

Branch `s38` (from main 476d5f1), node hold 12454 (aac7-n00); (m) unless labelled.

**Phase table, one node, defaults** (6.441e10 standard share, total 94.2 s; larger 8.5e10 share, total 140.7 s, peak 371.7 of 480 GB): init 12.6 s (13.4 %) / 16.2 s; bs wait for the seed thread 11.3 s (12.0 %) / 14.7; bs batch tier levels 1-23 21.8 s (23.1 %) / 31.7; bs mdev tier levels 24-25 13.7 s (14.5 %) / 22.2; recip 8.05 s (inside dm); dm total 34.4 s (36.5 %) / 55.3. Tier split: C form 29 products 24.4 s, B form 63 products 4.4 s. Init timeline: plane pools 5.2 s, seed thread 5.3 -> 24.0 s (waited 2.6 s for region pools), background mapping of the parity-1 halves 12.6 -> 26.8 s, level 1 starts at 25.6 s; at 8.5e10 mapping binds by 5.3 s (seeds joined 31.2 s, level 1 at 36.4 s). GPU view (rocprofv3, 7000 dispatches): busy per APU 56.3 / 56.3 / 55.4 / 43.6 s in an 81 s window; busiest kernels per APU (APU0): **k_addsub 10.35 s (APU3 4.5)**, k_gather 7.7, k_crt_batch 4.5, k_push3 4.4, k_b1r 4.4, k_maxidx 2.4, k_modq 1.6, k_bload 1.2.

**Ceilings of the other candidates** (mod): S-5 push-form B broadcast at most 1.0 s (below the 1 s bar); S-4 E2 fixed-slot allocator 1.3 s at 1e11 (0.5 %), the layout does not fragment at these shares; the 11.3 s seed wait is co-bound by seeds and mapping (mapping alone binds by 1.55 s here, 5.3 s at 8.5e10; belongs to `ECALC_VMM_BG`/`VMM_SAFE`); APU 3 idle in the tiers 12.7 s, perfect rebalancing 3.2 s at best (large design change); the C-tier all-to-all 10.0 s of 24.4 s exposed host wait (41 %) but the push kernel already runs at 221-253 GB/s and the transform is chunk-pipelined (bandwidth lever closed); k_maxidx 2.4 s (follow-up, S40).

**The lever: `DBIG_ADDSUB2=1`.** Cause: `k_addsub` gives each thread 16 consecutive limbs, so loads/stores of limb k are 128 B apart in a wave (64 cache lines per request), and every call is synchronous (171 calls on APU0, up to 1.34e9 limbs per quarter). Fix `k_addsub2`: the block's 4096 limbs move coalesced through a 32 KB XOR-swizzled LDS tile; same arithmetic, carry flags and output limb for limb (digits cannot change). One profiled pair: k_addsub 10.35 / 11.27 / 10.54 / 4.53 s -> k_addsub2 2.02 / 2.29 / 2.15 / 1.11 s; run total 93.7 -> 81.2 s (bs 45.1 -> 41.6, dm 34.3 -> 26.2, init 14.1 -> 13.3). Gates at 1e9 both arms: VERIFY OK, digits identical (11.43 s on, 13.21 s off).

**Multi-node confirmation and adoption (2026-10-10, m).** 1-node ABBA at 6.441e10 on four more nodes, 3 rounds each, stopped on p < 0.05, 48 of 48 runs VERIFY OK: B - A mean -12.27 s (CI half-width 1.20; aac7-n10), -12.51 (3.97; n11), -12.04 (2.34; n20), -12.27 (3.44; n21); arm A about 91-96 s, B about 80-83 s: **about -13 % on every node**. **Adopted as the default (`DBIG_ADDSUB2` default 1) by the user's rule "if it consistently reduces time, make it the default"**; `=0` restored the old kernel (switch since removed). Open then: a 2- and 4-node check (done in S43).

## NTT3P: can ecalc's large transforms run in 3 memory passes instead of 4? (design study, no code changed)

Labels (m), (mod), (a). Sources: S21 A37-Q4 NTT sweep, K13/K13b, `ecalc/ntt.c` (`make_plan`, `plan_auto`, `k_b16`, `k_b16r`, `k_b1r`), `estimate.py` / `mn_model.py` (`target-m --bw 47`, `aac7_s18 --bw 6`).

**Summary.** Best split at 2^31: **13 / 9 / 9** (b1 of 2^13 points, two strided 9-stage passes, all with 16-column 128 B segments) or **12 / 10 / 9** (keeps today's 2^12 b1; one 10-stage pass with 64 B segments); both fit the 64 KB LDS with no register staging. **Modelled saving per 2^31 forward: about 15 ms of 90.4 (17 %), range 5-24 ms**; the floor of any 3-pass plan is about 66 ms (3 x 17.3 ms NOP pass + 14 ms modmul). Per run (mod): 10 nodes about 1-2 s of 435 s (0.3 %); 576 nodes about 4 s (1.5-7) of 219-266 s (1.5-2 %), mostly NOT the 2^31 transform but the four-step pieces' row/column transforms of length 2^20-2^22, which run 3 passes today and would run 2. Effort M-L (2-3 weeks), correctness risk low (canonical outputs are unique), performance risk medium (1 block/CU, 64 B segments). No prior attempt at more than 7 strided stages or a 2^13 b1 existed. Recommendation: a 2-3 day microbench first (E0/E1), build only if the fat pass is within 10 % of the model. **Outcome: E0 was run in S24 and failed both gates (13/9/9 forward 90.6 ms against the gate <= 80 ms and today's 89.9; `results/SESSIONS.md §S22 / S23 / S24`); NTT_SIZE_STATS measured the whole transforms >= 2^27 at only 2.5 s per APU of 453 s at 10 nodes. Dropped.**

**Constraints.** `k_b16`/`k_b16r`: block 2^7 rows x 16 adjacent columns = 2048 points (128 B per row), 256 threads, `sh[128][17]` = 18.4 KB, 3 blocks/CU (LDS-limited), VGPR 46-66; `NTT_B16_STG` clamped to 3..7, so no strided pass is longer than 7 stages. `k_b1r`: 2^10-2^12 points per block (2^12 in production at 2^31, plan 121, 32 KB, 2 blocks/CU). LDS 64 KB per workgroup = exactly 8192 points; HBM 2.0 TB/s in NOP passes, copy kernels 2.2-2.4 TB/s (m). Pass logic is private to `ntt.c`.

**Pass counts now vs with 13/9/9 (computed).** logn 17-19: 2 / 2; **20-22: 3 / 2** (13+7, 13+8, 13+9); 23: 3 / 3 (13 + 9 = 22 stages); 24-26: 3 / 3; **27-30: 4 / 3**; **31 (plan 121, 5/7/7 + b1 12): 4 / 3**; 32-33: 4 / 3 (with C = 8 or 12+10+10). Two-pass coverage logn <= 22; three-pass coverage logn <= 31 (<= 33 with 64 B / 32 B segments). Splits enumerated at logn 31: 9/9/13 (recommended, s_lo 22, 13, 0, 1 block/CU), 9/10/12 (alternative, b1 untouched, 64 B segments), 10/10/11 (more segment risk), 11/10/10 with 32 B segments (not recommended: half-sector reads), 8/8/8/7 (4 passes: no gain, shows the pass count is the cost). All avoid s_lo 17 and 24.

**Cost model at 2^31** (forward, ms; 34.4 GB per pass; calibration S21 (m): NOP passes 17.3 / 19.0 / 17.1, b1-12 NOP 24.2, real 24.0 / 20.8 / 19.4 / 25.8; b1-12 costs 25.8/12 = 2.15 ms per stage all-in). Strided 9-stage 128 B pass 20.0 / 22.5 / 25 (optimistic / central +10 % for 1 block/CU / pessimistic +25 %); strided 10-stage 64 B 21.5 / 24.5 / 29; b1 13 26.5 / 30 / 33. Plan totals optimistic / central / pessimistic: 9/9/13 66.5 / 75.0 / 83 (saving **24 / 15 / 7 ms**); 9/10/12 67.3 / 72.8 / 79.8 (23 / 18 / 11); 10/10/11 66 / 74 / 85 (24 / 16 / 5). Once the passes are not HBM-bound the total is about 31 stages x 2.15 = 67 ms whatever the split, so choose by risk; the memory-only floor (3 x 34.4 GB at 2.2-2.4 TB/s) is 43-47 ms. ## N3 — host gaps in the batch tier (`BS_BATCH_PIPE`)

**Question.** OPPORTUNITIES N3 (`archive:results/O7b.md` §D rank 4): the batch tier's host work leaves the GPUs idle between and inside the lower binary-splitting levels. Does doing that host work in parallel and issuing each device's tiles back to back shorten the 1-node run at 6.441e10 digits, with identical digits?

**Change.** Branch `n3` (commits bcd764d, 9e774dd), switch `BS_BATCH_PIPE` (default 0 then), files `ecalc/rns_mul.c`, `rns_mul.h`, `binsplit.c` (batch-tier level loop only). With the switch: `binsplit_e` at levels with >= 4096 pairs and more than `BS_BALANCE_N` nodes: the `max_nl` scan is an OpenMP reduction, the next level's layout is computed one region per thread (regions are contiguous index ranges; a check stops the run if a node falls outside), the product list is one buffer kept across levels (no `calloc`/`free` of up to 1.9 GB per level) filled in parallel; `rns_mul_batch`: per-product scans (registration, `maxnc`, shared-B test, device of each result) run once in parallel and the device is reused (previously looked up three times, serially); `rns_mul_batch_local`: per-device order built by chunks in parallel in the same stable order, each device's tiles go to its stream back to back with descriptors through two pinned slots (the host fills tile t + 1 while tile t runs), the spill merge stays on the stream (VMM pools; host pools still merge on the CPU after a synchronisation), lengths read back once at the end (before: every tile waited twice and copied descriptors from pageable memory). Same kernels, arguments and order per stream, so digits are identical by construction.

**Gates (m, 2026-10-12 19:25-19:27, then after the rebase on main 740ac38 20:13-20:14)**: 2 nodes `BS_BATCH_PIPE=1` (`--build`, P24 forced) PASS, VERIFY OK, identical (19.18 s); 2 nodes default PASS (19.09 s); 1 node on PASS (11.45 s); 1 node default PASS (11.70 s); after the rebase 2 nodes and 1 node on PASS (19.90 s, 10.71 s).
