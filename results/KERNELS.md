## Topic summary

Single-node GPU and host kernels of the e-digit run, from the NTT constants (Phase 13) to the dbig add/sub family (October). Current state (checked against `ecalc/README.md`, RESULTS.md, and the code):

- **Adopted and now built in (their switches are gone from the code or README)**: K13 `NTT_MODMUL=1` (reduced-correction Barrett, exact, +5-12 % per transform); K13b `NTT_B1R=3` register-blocked b1 pass and `NTT_PLAN=1` (auto plan that moves the passes off the slow strides, +4-13 % per transform, -4.0 % compute at 4e10); S38/S40/S41 `DBIG_ADDSUB2`, `DBIG_MAXIDX_TOP`, `DBIG_QSEL` (user rule, 2026-10-10: -12.3 s, -1.6..-3.2 s, -0.9..-2.1 s at 1 node; -50 s at 4 nodes); S51 K2 `DBIG_ADDSUB3` and K3 `DBIG_MODQ_MONT` (built in; 1 node -2.03 s +- 1.38 on aac7); G515 `DIST_TWREC_G` (default since 2026-09-28, built in 2026-10-12); S115 `BI_MUL1_FAST` (decimal `mul_1` and fused span step, built in).
- **Defaults on by decision, switch still a fallback** (`ecalc/README.md`): `RNS_CRT_SCAN` (K4b, default 1 since 2026-10-12, D21), `P24_CRT_SCAN` (K4c, default 1 since 2026-10-13, D24), `BS_BATCH_PIPE` (N3, default 1 since 2026-10-12, D20).
- **Dropped (measured)**: K13 H2 MALL-chunked passes (`NTT_MALL`), H7 non-temporal stores, H6 occupancy variants (`NTT_B16_VAR`), `NTT_MODMUL=2` Shoup (loses 4-13 %), `NTT_B1R=4` (dominated by 3); S51 K4 `RNS_CRT_SUB` (no gain); S39 candidate A "raw-once k_gather" (S40 refuted the remote-bound assumption); NTT3P 3-pass 2^31 NTT (design study; its microbenchmark E0 failed the gate, `results/SESSIONS.md §S22 / S23 / S24`).
- **Live conclusions**: (1) the NTT passes are issue/latency-bound at 1.2-1.6 TB/s, not bandwidth-bound; there is no MALL cliff; (2) a stride penalty at s_lo 17 and 24 (about 12 % of a 2^31 transform) is an address-pattern effect that padding or rotation does not fix, so the plan avoids those strides; (3) by-value kernel argument structs with a runtime quarter index cost 112 B/lane of scratch and about 30 % of k_gather: use scalar-select (QSEL); (4) multi-node gains of the dbig kernels exceed the 1-node gains because the same kernels run inside the multi-node division; (5) gains below about 1 s per run are inside run-to-run noise (sd 1-2 s at 1 node); trust kernel-level stats (`DBIG_S51_STATS`) for them.
- **Open**: the k_gather strided write (next floor after QSEL), the k_addsub2 residue (about 1-1.5 s, weak model), k_modq beyond Montgomery, the s_lo 17 mechanism (HBM address hashing suspected), the four-prime `ec_words_to_dec4` (dominates k_crt24 and the four-prime k_crt_batch), K3 never exercised at 4e9 on CPX (modq counter 0), the level-1 host gap of N3 (about 2.3 s).
- **Superseded**: S38's "armed" ABBA (replaced by the 4-node confirmation inside S38); S39's raw-once gather plan (S40); S44's CPX figures are coverage only (CPX XCD devices share one APU's HBM).

**H3 variants.** MM 0 (`ec_mm`): FP64 Barrett + Dekker, four corrections (q off by +-2). MM 1: the quotient from the exact product against a two-term reciprocal pinvl = (1 - p pinv)/p, q = floor(fma(hi, pinv, fma(hi, pinvl, lo pinv))); bound: |x - ab/p| <= 0.5 + 2^-50, so q in {Q-1, Q, Q+1} and r in (-0.51p, 1.51p), all intermediate fma exact. Data products take one correction (lazy in [0, 2p), accepted by every butterfly input), twiddle products two (canonical); host check over 4e8 pairs per prime, all four primes: 0 wrong, r/p observed in [-0.5, 1.0]. MM 2 (Shoup): integer table with Shoup constants; two integer products per butterfly.

Whole transform ms (fwd | inv) and ratio to MM 0 (m): 2^20 0.058 | 0.059 (MM1 1.08x | 1.06x); 2^24 0.612 | 0.654 (**1.12x | 1.11x**); 2^28 11.52 | 12.16 (1.07x | 1.10x); 2^30 46.51 | 49.74 (1.07x | 1.09x); 2^31 104.4 | 110.9 (**1.07x | 1.07x**); 2^17 x 2^14 (2^31 pts) 48.84 | 52.40 (**1.11x**); MM2 is 0.88-0.96x everywhere.

**H2 detail.** For the same pass structure ns/point is identical below and above 256 MB (e.g. L 14 pass [10..13]: 1731, 1771, 1693, 1705 GB/s at 128 MB, 256 MB, 512 MB, 16 GB). Pass rates (steady): b16 with s_lo 10-16 1.55-1.65 TB/s; b1 pass 1.21-1.24 TB/s, the slowest everywhere (28 % of a 2^31 forward); partial last b16 pass of 1-4 stages 1.45-1.94 TB/s. By s_lo, forward: 10-16 1.55-1.63 TB/s; **17: 1.29-1.33**; 18: 1.45; 19-23: 1.53-1.58; **24: 1.18 TB/s**. `NTT_MALL=lc` ratio to default: lc 20 0.58-0.69, lc 22 0.82-0.87, lc 24 0.97-1.02, best **1.04** at 2^26 only (2^20 batch and 2^26 single, lc 25): current pass/tile sizes sit on the right side; the switch stayed for the record.

**H7 detail** (pack plain -> NT, ms): 2^22 0.087 -> 0.208; 2^26 2.455 -> 3.047; 2^28 9.784 -> 12.47; 2^30 47.98 -> 50.53; unpack flat; the transform after a pack costs the same either way. Side finding: the plain pack runs at only 360-770 GB/s (scattered-store transpose; at 2^30 it takes as long as a whole 2^30 forward, 48 ms); an LDS-tiled transpose like `k_unpacktw`'s is the lever (belongs to the four-step path).

**H6 detail.** `k_b16r`: VGPR 46-66, LDS 18.4 KB, 3 waves/SIMD; `k_b1`: VGPR 18-22, LDS 12 KB, 5 waves. VAR1 (unpadded LDS + global twiddle table, 4 blocks/CU) speeds good passes slightly (2^24 pass [10..16] 1658 -> 1726 GB/s fwd, 1493 -> 1687 inv) but slows the s_lo 17 pass (1245 -> 992); VAR2 (block order) leaves s_lo 24 unchanged (1173 -> 1176) and makes 17 worse (1290 -> 1232). Whole transform ratios VAR1/2/3 0.96-1.02; MM1 1.04-1.11. Occupancy is not the limiter; a fix would be a padded or rotated plane layout (a plane-format design item).

**4e10 end to end** (m, one node s24-26, reference evicted, digits identical): MM0 79.06 s (bs 32.7 + dm 26.1), MM1 80.67 s (bs 32.0 + dm 25.9 = 58.0), MM0 again 81.62 s (bs 32.3 + dm 26.0 = 58.4); init (20-23 s) varies more than the effect; adopting MM1 is cheap (exact, local to `ntt.c`) but worth about 0.4 s at 4e10. **Acceptance**: `mnaccept unit,e9` on ff83794 all 8 unit PASS; e9 identical in both bases (19.26 s base 10, 25.99 s base 2).

**Open (then).** Stride penalty (about 12 % at 2^31); the b1 pass at 1.22 TB/s (answered by K13b's register-blocked b1); MM1's lazy products reach every `ntt.c` kernel, `ntt3.c` radix-3 and `ntt2.c` call `ec_mm` on canonical values and are covered by the §4c radix-3 check.

## K13b — Phase 13b agent K: the b1 pass and the stride penalty (PLAN §31, row K)

| item | verdict | headline (m) |
|---|---|---|
| **b1 register-blocked (`NTT_B1R=3`)** | **Wins at 2^20 points and up**: b1 pass 1.20-1.33x faster (1.26 -> 1.52 TB/s at 2^31, level with the b16 passes); whole transforms +4-13 %. `B1R=4` (16 points/thread, 2 waves/SIMD) is slower than 3 | 2^31 b1 pass 27.25 -> 22.68 ms fwd, 27.56 -> 22.86 inv; 2^31 fwd 104.7 -> 100.4 ms |

Mechanism (HBM channel/bank hashing over address bits 20-26, 27-33) not pinned down | see below |
| **stride penalty: fix (`NTT_PLAN`)** | **The plan moves the passes off the slow strides.** At 2^31: b1 on 2^12 points, b16 passes bottom-up: s_lo 26, 19, 12 instead of 24, 17, 10: **fwd 1.06x, inv 1.12x**. **Bigger side effect**: where the default plan ends in a b16 pass of 1-2 stages (logn 11, 12, 18, 19, 25, 26, 32, 33) a b1 of 2^11 or 2^12 points removes that pass: **1.25-1.40x at 2^25 and 2^26** | 2^25 1.465 -> 1.049 ms fwd; 2^26 2.806 -> 2.251; 2^31 104.7 -> 99.2 |
| **4e10, `NTT_B1R=3 NTT_PLAN=1`** | digits identical; compute **-4.0 %** over three pairs, ranges do not overlap | bs + dm 46.4 -> 44.5 s |

**Design of the b1 pass.** A block is one 2^lb-point chunk with 2^(lb-LGV) threads, each keeping V = 2^LGV points in registers; stages run in ceil(lb/LGV) groups with one XOR-swizzled LDS exchange between groups (3 exchanges at lb 10, LGV 3, instead of 10 LDS round trips); first-forward load and last-inverse store are coalesced; twiddles from one global per-stage table (4096 entries). The butterflies, modmul and canonicalisation are the paper kernel's, so outputs are bit-identical. LGV 3: 48-54 VGPR, 8 KB LDS per 128-thread block (4 waves/SIMD); LGV 4: 82-88 VGPR (2 waves/SIMD). b1 pass rate (GB/s, fwd | inv): 2^24 paper 1188 | 1282 -> B1R3 lb10 **1512 | 1530**; 2^31 1261 | 1247 -> **1515 | 1503** (B1R4 1420 | 1482; lb 11 1378 | 1410; lb 12 1253 | 1294). At MM 0 the gain is 1.14-1.21x. Longer b1 blocks (lb 11, 12) cost 9 % and 20 % more than lb 10 and pay only where they save a whole pass.

**Stride microbenchmark** (`kb_strd`, 128 rows x 16 columns per block, 2^31-point plane, GB/s, pad 0): s 10-16 2562-2665; **s 17 1689**; s 18-23 2266-2458; **s 24 1459**; padded 128 B / 1 KB / 4 KB at s 17: 1941 / 1898 / 1884; rotation 1626 / 1622. Same pattern at 2^28 points (s 17: 1717 vs 2443-2826). So a padded or rotated plane layout would not remove it (and would change the plane format outside `ntt.c`): not built. Pass rate by s_lo in a real transform (L 31, 7 stages, fwd | inv): 10-16 1599-1627 | 1547-1581; **17 1338 | 1102**; 18-23 1544-1561; **24 1136 | 1135**; 6-stage tile at the top 1063 (s_lo 25), 5-stage 1316 (s_lo 26). In the default plan only logn = 3 mod 7 (17, 24, 31) meets s_lo 17 or 24, so **only 2^24 and 2^31 are affected**; with b1 of 2^10, no 3 x 7 plan avoids both. `NTT_PLAN=1` picks 110 at logn 11, 18, 25, 32 and 120 at 12, 19, 26, 33 (one pass fewer), 121 at logn 31, default elsewhere. Per pass at 2^31 (ms fwd): default 30.35 / 25.64 / 21.11 / b1 27.40 = 104.5; B1R4 + P121 26.14 / 22.37 / 21.32 / 28.42 = **98.2** (inv 96.9).

**Whole transforms, recommended pair `B1R=3 PLAN=1`** (ratio to the default, fwd | inv | fused inv_pw; default ms in brackets): 2^24 (0.548) 1.07 | 1.07 | 1.06; **2^25 (1.238) 1.21 | 1.28 | 1.28; 2^26 (2.723) 1.31 | 1.32 | 1.28**; 2^28 (10.77) 1.07 | 1.06 | 1.04; 2^30 (43.84) 1.06 | 1.06 | 1.05; **2^31 (98.16 | 104.8 | 109.1) 1.11 | 1.15 | 1.14**; 2^14 x 2^17 1.13 | 1.12 | 1.09; 2^20 x 2^11 1.09 | 1.08 | 1.06. No layout loses at 2^20 points or more (2^20: +4 %, launch-bound). Batch 1 (s24-30, rates 4-6 % lower) confirms; the best explicit plans: B1R3 + P111 1.40x at 2^25, B1R4 + P121 1.25x at 2^26 and 1.06 | 1.12 at 2^31.

**4e10 at size 1** (m, job 21065 and 21070, digits identical where compared). Pair 1: on 44.3 s (bs 23.68 + dm 20.59) vs defaults 45.9 s (bs 25.01 + dm 20.84); batch 5 pairs: off 46.5, 46.7 vs on 45.0, 44.3. ## K4b — `k_crt_batch`: the per-chunk carry chain as a parallel carry-lookahead

**Question.** Does resolving the CRT kernel's per-chunk carry chain in parallel (instead of a 256-step serial loop by one thread) shorten the 1-node run at 6.441e10 digits? Baseline: `k_crt_batch` takes 4.5-4.8 s per APU at 1 node (m, `results/KERNELS.md §S39` row 3).

**Change.** Branch `k4b`, switch `RNS_CRT_SCAN` (0 serial; 1 parallel), files `ecalc/rns_mul.c`, `rns_int.h` (`struct gconst` field `scan`), new test `tests/t_crtk.c`. Per chunk of 256 coefficients, thread j forms w_j = V_j + CY_{j-1} (<= B + 4); the serial overflow o_j = gen_j | (prop_j & o_{j-1}), gen = w >= B, prop = w = B - 1; two wave ballots give the masks, every thread adds A + G (A = gen | prop, G = gen) over 256 bits and reads its carry-in as bit j of (A + G) ^ A ^ G. Barriers per chunk: 3 instead of 5. Serial path is the reference (`t_crtk` compares every limb and spill word).

**Results (m).** `t_crtk 29`/`27` equivalence: 48 cases (3 and 4 primes), all identical. Kernel, C form 2^29 / 65536 stripes: three primes **30.18 -> 13.65 ms (2.21x, 569 -> 1259 GB/s)**; four primes 49.85 -> 34.11 ms (1.46x); 2^27 / 16384: 8.02 -> 3.95 ms (2.03x) / 12.54 -> 8.56 ms (1.47x). Gates (2 n and 1 n, off and on; before the rebase and after two rebases on main, the last with P24 for every multi-node product): all PASS, VERIFY OK, digits identical, segv 0; `t_mul 20` 169 checks and `t_strategy 24 2 V` 12 checks OK both arms. **ABBA 1 node, 6.441e10, 4 rounds (16 runs, all VERIFY OK): B - A = -2.52 s, 95 % CI [-4.19, -0.85]** (per round -3.6, -1.4, -3.2, -1.9 s; p < 0.05); arm means A 71.47 s, B 68.95 s (-3.5 %). Modelled 2.4-2.6 s of kernel time per APU (4.5-4.8 s at 2.21x).

**Verdict.** Adopt candidate, above the 2.0 s assumed in OPPORTUNITIES; merged switch off, then adopted as default 1 (D21, 2026-10-12, `ecalc/README.md`). **Open**: the four-prime form gains less (1.46x) because it is bound by `ec_words_to_dec4`'s sixteen divisions, not by the chain (a cheaper four-word-to-decimal conversion is the next step); multi-node timing not measured here (2-node gates show digits only); `k_crt24` has the same chain (done in K4c). Driver `archive:drivers/k4b/`.

## K4c — `k_crt24`: the P24 CRT's per-chunk carry chain as a parallel carry-lookahead

**Question.** Does K4b's carry-lookahead applied to `k_crt24` (`ecalc/p24_crt.c`, the form of every multi-node product since D18, `results/LAUNCH_DEFAULTS.md §DEF`) shorten the 2-node run at 6.441e10 digits per node?

**Change.** Branch `k4c`, new switch `P24_CRT_SCAN` (0 serial; 1 parallel), files `p24_crt.c` (`k_crt24`, `p24_crt_launch`), new test `tests/t_crt24k.c`. A new switch rather than `RNS_CRT_SCAN` (which had become default by D21 on 1-node data while this branch was open). A chunk of 256 points covers up to 342 limbs (each sums at most three points, quotient CY <= 2, carry-in <= 3, w_i <= B + 2); each thread owns limbs t and t + 256; four wave ballots give the masks of 512 limbs; same barrier count (5), the 342-step one-thread loop is gone.

**Results (m).** `t_crt24k`: 279 checks (9 shapes x 6 coefficient kinds x up to 3 ranks) all identical; `t_p24` against the GMP model 78594 checks OK both switches. Kernel at 2^30 points per rank (rows 4096 / 8192 / 16384): **157.96 / 158.39 / 158.76 -> 101.95 / 101.95 / 101.26 ms, 1.55-1.57x (290 -> 450 GB/s)**. Gates on two commits (2 n and 1 n off/on): PASS x4 each, P24 in use at 2 n. Profiling round: node 0 `crt` sum per run A 4.13 / 4.25 s -> B 2.95 / 2.94 s: **-1.24 s per run** (m, 1 round). **ABBA 2 nodes, 6.441e10/node, 4 rounds (16 runs, VERIFY OK): total B - A = -1.89 s, 95 % CI [-7.51, +3.73]** (per round -2.8, +2.0, -6.3, -0.5; not significant); A 126.28 s, B 124.39 s; dm -0.55 s [-3.00, +1.90], bs -0.43 s [-1.67, +0.82]. Modelled kernel saving -1.49 s per run (4.19 s CRT time at 1.55x).

**Verdict.** The kernel gain is clear, the wall claim unresolved (the A arm had two slow runs, 131.0 and 131.4 s, against B 122.7-125.9 s; resolving -1.2 s at a 3.5 s per-round spread needs about 40 rounds (mod)). Merged switch off, then adopted as default 1 on the kernel evidence (D24, 2026-10-13). **Open**: `ec_words_to_dec4` now dominates the kernel (K4d); the CRT share at larger node counts is not measured (per-node CRT time stays about the same, mod). Drivers `archive:drivers/k4c/`.

## S38: the next single-node speed lever. Found: the dbig add/sub kernel (k_addsub) ran at 36-84 GB/s; DBIG_ADDSUB2=1 (coalesced) cuts 10.4 -> 2.0 s of GPU time per APU
