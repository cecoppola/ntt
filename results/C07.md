## 1. Method and its limits

- Node: aac6 `aac6-cpx-a` (PPAC_MI300A_CPX, 24 devices = 4 APUs x 6 XCDs, 22.9 GB each). ecalc runs on it with `ROCR_VISIBLE_DEVICES=0,6,12,18` (one XCD per APU, four ranks, each with 1/6 of an APU's compute and the xGMI links of its APU), `RNS_INIT_POOL_LOG=29 ECALC_PLANE_CAP=2^30`. **So compute is about 6x slower per device than on the real APU while the link is the same: the exchange share is understated and per-call latencies (host barrier, stream sync, launch) are overstated.** Ratios are used with that in mind; every production figure below is an extrapolation (mod/as) and one rocprofv3 trace of a 1-node run on aac7 would settle it (not run: no aac7 in this task).

All four APUs are identical (compute 3.50 / 3.49 / 3.48 / 3.48 s, push 0.37 s each; no skew: host wait per rank post|wait 0.010|0.208 / 0.018|0.210 / 0.016|0.209 / 0.010|0.209 s). By product size:

|---|---|---|---|---|---|---|---|

Reading: the host wait is 29 % of wall for the big products (S38 production: 41 %) while the GPU is computing 84 % of that wall. The host blocks in `chunk_wait` (stream sync + 4-thread barrier) for chunk k-1 **while chunk k's row pass is already running**; it measures the exchange's latency, not an idle GPU. The big-product GPU idle splits into: pure exposed transfer 3.3 % (the last chunk of each of the 9 transforms per product; K = 8 chunks, `inflight` = 1), a host gap between `k_modq_m` and the first `k_gather` of each product (0.13 s over the 8 biggest products, about 5 %), and per-prime `hipStreamSynchronize` / launch gaps.

## 3. K7: two candidate fixes

Model basis (CPX B product, m): transforms 1.70 + bload 0.19 on APUs 0-2, the rest (CRT 0.27, add/sub, host) shared. A perfect 4-way split moves 3/4 of the 1.89 s: 2.41 -> about 1.94 s = **-0.47 s per 2.41 s = -19.6 % of the B-form time**. At production the B form is 4.4 s (6.441e10) and 3.35 s (8.5e10, S38): **-0.86 s and -0.66 s (mod)**.

**Measured today's B4** (existing code, `RNS_STRATEGY_FORM=B4`, ABBA x4 = 8 runs each, B-form product time, m): B 2.367 s (2.36-2.38), B4 2.434 s (2.43-2.46): **B4 is +0.067 s = +2.8 % slower**, VERIFY OK in the 8 retained logs (all 16 runs rc 0). Profile of B4: APU 0-2 transforms drop 1.70 -> 1.36 s (-20 %) but k_bload rises 0.19 -> 0.31 s and the new split kernels `k_bsplit<1>/<3>` cost 0.26 s; APU 3 carries only 0.72 s of transforms (APU 3 busy 1.45 vs 2.28 s). Two reasons it does not pay: (a) APU 3 does the forward of Y's upper residue (1.5 n) but none of the inverse, so the split is 2.5 n vs 1.5 n, not balanced; (b) the split and the peer reads (APU 3's plane read remotely) add 0.38 s.

| | K7-a: finish B4 | K7-b: independent products on the idle APU |
|---|---|---|
| idea | keep B4's math; (1) fuse `k_bsplit` into the forward pass's last stage and the peer read into the pointwise (no separate kernels, no extra bload), (2) hand APU 3 a share of the inverse: after the pointwise APUs 0-2 push their upper-half spectra to APU 3 (3 x n/2), which inverts the upper residues, so the loads become 2.0 n / 2.0 n / 2.0 n / 2.25 n | the tree node P = Pl.Pr, Q = Ql.Qr, T = Tl.Qr + Pl.Tr are 3-4 independent products; run product j with primes on APUs (j, j+1, j+2) mod 4 so every APU is busy, two products in flight |
| gain, 1 node | transforms+bload: 1.89 -> about 1.5 s of 2.41 s (APU 0-2 ntt 1.36 -> 1.20 s, overhead removed): **-0.45 s per 2.41 s (-19 %); 0.8 s at 6.441e10, 0.6 s at 8.5e10 (mod)** | the same ceiling (-25 % of the transform part) but needs 2 products' planes at once: B's extra plane memory (16 B/point/APU) doubles; B already fits only up to a size, so it falls back to C exactly where it would matter |
| 576 (in-node) | 0.3-0.7 s (as; node-local B products are only the bs top levels) | not applicable (pool pressure at the target is the binding limit) |
| effort | M: 2-3 days (b_core/B4 split kernels in `rns_dist.c`, owner a08 for gather kernels / the dist owner; new switch `RNS_STRATEGY_FORM=B5`), gates: t_strategy, e9 both bases, 4e10 | L: 5+ days, scheduling in `rns_dist.c` + bs level code, memory model change |
| risk | low-medium (digits are exact residues; `RNS_STRATEGY_CHECK=1` re-forms by C and aborts on a difference) | high (memory, ordering) |

## 4. K6: two candidate fixes

The ceiling is not 10 s. GPU idle in big C products is 13 % of wall; applied to the 24.4 s C time at 6.441e10 that is **at most 3.2 s (mod)**, made of exposed transfer (37 % of the 4.4 s push time = 1.6 s, mod) and ~1.6 s of host-side gaps. Hiding all exposed tails is not possible (the very last chunk has nothing behind it), so realistic is the 2/3 of the tails plus the sync gaps: **1-2 s at 1 node (mod)**, 1-2 % of 94 s.

| | K6-a: chain the transforms (hide the 3 tails per prime) | K6-b: device-side exchange (no host barrier), depth 2 |
|---|---|---|
| idea | per prime there are three exposed tails: fwd A's last chunk, fwd B's last chunk, the inverse's first chunk. Enqueue B's row passes (and prime p+1's gather and fwd A rows) **before** waiting for the previous transform's last chunk, i.e. one 16-chunk pipeline [A0..A7, B0..B7] with A's unpacks after B's first row passes. Needs `comm_xgmi` to allow 2 chunks in flight (`inflight` 2: per-slot buffer pointers; today single `G.rb/G.bytes/G.s`) or a per-chunk event wait for the H1 hazard (receiver's unpack of region k must precede the next push into region k) and drop the per-prime `hipStreamSynchronize`s in `dist_core` | the push kernel waits on a device flag written by the peer's pack (xGMI store) instead of the host barrier + stream sync; the host only enqueues; removes the post/wait latency, the skew risk and the per-chunk gap |
| gain, 1 node | hides 2 of 3 tails: about 1.1 s + sync gaps 0.2-0.3 s = **1.3-1.4 s (mod)** | up to the whole 3.2 s (mod), realistically 2 s |
| gain, 576 in-node | 0.4-0.8 s (as: the bs top levels' C share only) | 0.6-1.2 s (as) |
| memory | none (same sbuf/rbuf; per-chunk regions already distinct) | none |
| effort | M-L: 4-5 days (touches `ntt_dist.c`, `comm_xgmi.c` (owner a01) and `rns_dist.c dist_core`); switch `DIST_CHAIN=1` | L: 8-10 days, new device-side protocol; shares work with c06/c03 transport code |
| risk | medium (H1 hazard, ordering; RB_WAIT test `DIST_TEST_LAG_MS` exists; digits unchanged, an ordering) | high (device-side signalling, hangs) |

Not a lever: bandwidth (push at 221-253 GB/s per APU, S38 / X13); the K = 8 chunk count alone (12.5 % tail is the floor of any single-buffer pipeline).
Side finding for the gather owner: in the C tier `k_gather` is the biggest non-transform kernel (7.7 s on APU 0 at 6.441e10, larger than the whole push, 4.4 s).

## 5. Recommendation

1. Do **neither** as a standalone item now: K7's honest ceiling is 0.5-0.9 s and K6's 1-2 s, against S38's 3.2 s and 10 s. The two numbers in the opportunity list should be replaced by these.
2. If one is built, take **K7-a** (finish B4 as B5): lowest risk, digits checkable by C, 0.6-0.9 s at 1 node and it also fixes B4's known 3-7 % loss (measured +2.8 % here). Build only after one aac7 `ECALC_INIT_TL=1` + rocprofv3 run confirms the B-form share (4.4 s) and the unattributed 3-4 s of APU 3 gap.
3. K6-a after that, only if a trace on aac7 shows the C-tier idle really is >= 10 % of its wall (here 13 % for the big products on a node with 6x less compute per device; the real APU spends more of the wall in the exchange, so the true figure may be higher).
4. The one cheap, no-engine step: a 1-node aac7 run with rocprofv3 + `C07_TS=1` (branch binary, ~3 min of node time) to replace the CPX extrapolations by measurements.
