# O9 (TASKS 12): why the non-power-of-2 `layv` exchange looks slower than `layeq`

Status 2026-10-11 23:50 ET: diagnosis from code and existing data done; **no code change** (no clear fix); one aac7 queue item armed
(`65_o9_layv.sh`, 6 nodes, EST 45 min, runs after item 60) to confirm it. Labels: **m** measured, **d** derived by arithmetic from measured
numbers, **mod** modelled, **a** assumed. Branch `o9` off main 0298fe2.

## 1. Answer in short

1. **The "2.3x slower per thread" (S48) is mostly how it was measured, not the exchange.** Under `COMM_LAYER_INTER2` (on in the aac7 line)
   two `layv` inter stages are in flight per mesh and `t_post` counts the overlap twice (C02). From the post-to-post span (GB / sum of `t_call`) the
   6-node `layv` stage runs at 12.4-15.7 GB/s per APU thread against `layeq`'s 17.3-19.1 at 4 nodes: a factor of **0.70-0.84** (d), not 0.41.
2. **The `layv` code path costs nothing measurable at the same group size.** C06's 4-node run with `DIST_GEN=1` (every 4-node level on the
   general map, i.e. `layv`, same aac7 line with X2) took **179.45 s** (m, one run, NIC group unknown, the line of that day); `layeq` 4-node runs in fast mode take 180.4-185.6 s
   (S48 181.97 / 181.62, m). Code reading agrees (section 2): the same SHMEM path, no rounds, no padding, balanced counts.
3. **What is left is the group size g = 6, not `layv`:** smaller per-peer slabs (60 MB vs 134 MB per peer per exchange at 4 nodes, m, C02), so the
   fixed per-exchange cost weighs more; 5 peers instead of 3 (peer order / incast term, C02 1.3); and more nodes in each exchange's critical path,
   so the per-exchange skew (the slowest of 6 x 4 APU threads) grows. In the same 6-node run (S48 n6_r1) the 2-node level of `[2,6]` (`layeq`, g = 2)
   runs at 17.2 GB/s per thread with 0.1 s of skew wait per thread, the 6-node level (`layv`) at a 12.4-13.3 span rate with 6.9-19.3 s of skew wait (m).
4. **No clear fix in `comm_layered.c` / `comm_shmem.c`.** The one structural candidate (publish the receive offsets before the intra stage, section 3)
   needs a separate intra-stage buffer (+A bytes per v-slot, about +50 % of the v-slot pair, mod) and a split transport API (a change across several files),
   and it only helps if the skew wait is a real loss rather than wait moved from one place to another. The armed item decides that (section 4).

## 2. `layv` vs `layeq`, by code (main 0298fe2)

| | `layeq` (`y_alltoall`, pow2 map, `ntt_dist`) | `layv` (`y_alltoallv2`, general map, `gen_fwd` / `gen_inv_pw`) |
|---|---|---|
| chunks per pass | `DIST_CHUNKS` = 8 | `DIST_CHUNKS` = 8 (`gplan_build`) |
| counts | equal slabs | `part0`/`partn`: rows and columns split within 1 row over 4 g ranks: **balanced**, no padding (exact segments, B7) |
| per-exchange host work | intra all-to-all + `block_transpose`, 2 stream syncs | + `vtab_build`: a host all-gather of the count table over the 4 APU threads and 2 mallocs; the reorders are `bcopy` kernels; 2 stream syncs |
| SHMEM path | `s_alltoall`: publish offsets, pusher thread (OFI), signals, `arrive` | `s_alltoallv`: the same publish / push / arrive. With `COMM_LAYER_VSLOT_POOL=1` the buffers are in the pool, so **no rounds and no staging** (the `ROUND_MB` path is skipped) |
| in flight | one inter stage: post k right after completing k-1 | X2: post k (on the second communicator), then complete k-1: two inter stages |
| where the publish of k sits | right after the completion of k-1, which needs every peer: the publishes are aligned, `roff` ~ 0 | after the node's own intra stage of k and before it completes k-1: not aligned, so node skew shows up as `roff` |

Consequence for reading xstats: the `roff` / `sig` / `other` split is not comparable between the two kinds. `layeq`'s skew is hidden in the
completion of k-1 (`sig` / `other`), `layv`'s shows up as `roff`. Only `t_wait` and the span (`t_call` under X2, `t_post` for one in flight) compare.

Per-exchange extras of `layv` (the all-gather, the mallocs) are microseconds against 20-40 ms exchanges (a); the 4-node `DIST_GEN=1` total (item 2 above)
bounds their sum at no measurable cost.

## 3. Fix candidates looked at

| candidate | what | why not now |
|---|---|---|
| early publish | publish the receive offsets of k as soon as slot k is free and the counts are known, before the node's own intra stage of k, so peers' data flows in while a late node finishes its intra stage | x1 (the intra stage's output) lives in the x3 receive area today; a separate x1 costs +A bytes per slot (about +50 % of the v-slot pair, mod; the 576-node memory margin is 13.0 GB at 3.82e13, L4); the publish is inside `comm_alltoallv`, so the transports need a split publish / post API (`comm.h` ops, `comm_shmem.c`, `comm_layered.c`, and stubs elsewhere). Gain: at most the transfer time hidden under a late node's intra stage; unknown until the skew is shown to be a loss (section 4) |
| peer schedules `rr` / `winK` | interleave chunks over peers | C02's microbenchmark: rr 15.65, win2 17.88 vs rot / pair 21.0 GB/s per PE (m): no build (TASKS 38) |
| `rot` (X1, in code) | rotated start | S27 / RESULTS: +20 % transport rate, 0 wall (m) |
| cache the count table | skip `vtab_build`'s host all-gather when the counts repeat | microseconds per exchange (a); the 4-node `DIST_GEN=1` total shows no `layv` overhead to win back |
| `COMM_LAYER_INTER2=0` at 6 nodes | one in flight, aligned publishes | X2 was adopted for its wall gain; this only moves `roff` back into `sig` |
