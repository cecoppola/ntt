# A09 -- init seconds, the mapper lock, and what the background mapper buys (N9 / K8)

Analysis only (CPU, existing aac7 logs; no cluster job, no code change). Times in seconds since `rns_init` begins unless noted.
Every number is labelled (m) measured, (mod) modelled or (a) assumed. Parsing script: kept in the agent scratchpad, not tracked.

## 1. Data
- `~/s48/log/n{1,2,4,6}_r{1,2}.log` (aac7, `ECALC_INIT_TL=1`, 6.441e10 digits per node, 2 runs per node count; 26 process timelines).
- `~/sess1011b/t09/log` (4 nodes, 11 runs: 8 normal, 3 in the "slow fabric" mode of T09) and `~/t12/real1/log/r001.log` (4 nodes, slow).
- `~/batch1011/T1/jobA/log` (S46 reproducer, 1e10 digits, 0.0625 GiB chunks): no init timeline lines in it, so it only gives wall times.
- results/S22.md 3.1 (1 node, 6 reps), S34.md, S38.md, S46.md. results/S35.md does not exist (S35 is a section of S34.md).
- Caveat: multi-node logs interleave the processes without a rank label, so per-node values are means/maxima over the processes and APUs.

- Normal 4-node runs of T09 (8 runs) give level 1 at 28.2-30.7 s, same as s48 (29.2, 29.6): the table is reproducible (m).
- Slow-fabric runs (3 in T09, T12 r001): level 1 at 38-44 s, joined 37.8-43.4 s, mapping 25-30 % slower (queue 10.6-10.9 s) but the last
  background chunk (32.5-33.9 s mean) is not what binds; it is a different delay (not analysed here).
- Queue by APU is unfair but work-conserving: at 1 node the queue ranged 3.5-7.4 s between APUs; the last APU always finishes at
  (start + total chunks x 0.25 s), whoever it is (n1: half-mapped at 22.4 / 19.8 s = 13.5 + 36 chunks x 0.246, mod).
- So the "3-11 s queued for the mapper lock" (S38) is not waste on top of the mapping: it is the other three APUs' mapping time
  (the global `g_vmm_map_mx` makes the four mapper threads of a process run one after another). Removing the queue by reordering is
  impossible; only running the calls concurrently (as the synchronous phase does) could shorten it.

## 3. What binds level 1 (m)
- 1 node: seeds bind. Seed thread ends 23.6-24.2, last mapping 21.1-21.4 (mean) / 22.8-23.3 (max), level 1 24.1-24.7.
- 2 and 4 nodes: mapping binds, narrowly. Seeds are joined at 26.4-28.2; level 1 starts 1.4-1.5 s (2n) and 1.4-2.5 s (4n) later, and the
  APUs wait 1.8-2.0 s (2n), 4.0-8.3 s summed over the node (4n) for chunks of the parity-1 half.
- Under both, the margin between the two chains is about 1.5 s: any single fix is worth at most ~1.5 s (mod), both at most ~3 s.
- Per chunk the background mapping (0.25 s per chunk, serialised, with the seed threads running) is slower in aggregate than the
  synchronous phase (0.155 s per chunk aggregate at 1 node, 0.19 at 2/4 nodes; 4 APUs concurrent): about 1.3-1.6x. Part of this is
  driver parallelism the lock forbids, part is CPU contention with the seeds (not separable from these logs).

## 4. What the background mapper saves against `ECALC_VMM_BG=0` (synchronous), at the current map rate
Model (mod): with `BG=0` every chunk is mapped in `db_vmm_arena_alloc`, the "hook" ends later by (chunks that now go to the background)
x (synchronous per-chunk time), and the seeds, idle until the hook, then need their remaining ~10.5-11 s (m: seed end - hook =
10.9 / 11.3 / 10.3 s at 1/2/4 nodes).

| nodes | extra hook time (mod) | level 1 start with BG=0 (mod) | now (m) | cost of BG=0 (mod) |
|---|---|---|---|---|
| 1 | 11 chunks x 0.62 = 6.9 | 13.2 + 6.9 + 10.9 = 31.0 | 24.4 | +6.6 |
| 2 | 15 x 0.77 = 11.5 | 16.1 + 11.5 + 11.3 = 38.9 | 28.3 | +10.6 |
| 4 | 17 x 0.77 = 13.1 | 16.3 + 13.1 + 10.3 = 39.7 | 29.4 | +10.3 |

- Measured: S34 soak, 2 nodes, `BG=0` +20.0 s (+9.8 %), 1 node +1.4 s (S34.md; walls quantised to 20 s at 2 nodes, so +-10 s; older code
  state). S46 reproducer (1e10 digits, tiny arena): BG=0 ecalc time 34.5 s against 35.6 s base and 35.4 s with userfaultfd (unpaired),
  i.e. at 1e10 digits the mapper is irrelevant (mapping is ~13x smaller there); it says nothing about 6.4e10 per node.
- The model (+7 to +11 s) is about half the S34 figure and the 1-node model (+6.6) contradicts S34's +1.4. The disagreement is unresolved;
  one paired run pair (BG=0 vs default, `ECALC_INIT_TL=1`, 1 and 2 nodes) would settle it. Not done (no cluster work in this task).

## 5. At the target map rate (7x faster, a)
Assume plane pools ~1 s, every VMM call 7x faster (a, uniform; S22 3.1 uses the same 7x).
- Seed thread pre-hook work is ~4.3 s (m: buffers + 2 chunks, seed start 5.8 -> 10.1 at 1 node). Full synchronous mapping then takes
  1 + (21..27 chunks x 0.62..0.77 / 7) = 2.9 (1n) to 4.0 s (4n) (mod), which is before the seed thread finishes its pre-hook work (5.3 s).
  So with `BG=0` the seeds would not wait at all: cost ~0 s (mod, a), same as the background mapper. The seed chain then ends at ~15.8 s
  against the 16.5 s init floor (S22 3.1), so neither mapping nor seeds bind.
- At the target the background mapper therefore saves ~0 s and keeps the whole crash surface (the segfault in `hipMemMap` inside `vmm_bg_map`,
  the lock-order deadlock).

## 6. Proposal
1. **Keep the background mapper for now (default unchanged), with userfaultfd on.** At today's rate it is worth ~7-11 s (mod) at 1-4 nodes
   (S34 measured +20 s at 2 nodes). userfaultfd removed the hangs (0/104 against 22/105, m) but nothing in the S46 data tests the original rc 139
   segfault (4/422 = 1 %, m, S34; 0 segfaults in every S46 arm). Whether userfaultfd also removes it is open (a: same libfabric/ROCr cause).
2. **Simplify when the faster mapping exists: choose synchronous mapping automatically.** After the synchronous parity-0 phase the rate is
   known (s per chunk). If (remaining chunks x rate) < the seed thread's pre-hook work (~4 s, or a fixed 3 s), map them synchronously and start
   no mapper thread; otherwise keep the thread. Mechanical (`db_vmm_arena_alloc`, `m1 = m0`), digits unaffected, same code path as `BG=0`
   that already ran 104/104 clean. Behind a switch (`ECALC_VMM_BG=auto`), default off. Not implemented here (no code changes allowed).
   Remove the mapper entirely (delete `vmm_bg_map`, `ECALC_VMM_BG=2`, `ECALC_VMM_SAFE`, the S46 repro switches) only after the 7x rate is measured.
3. Lower-risk init speed-ups at today's rate (all mod; each <= ~1.5 s, since the two chains differ by ~1.5 s):
   - Publish the synchronous parity-0 chunks one by one (set `mapped` per chunk, seeds wait per chunk, instead of "hook done" after all
     10): the seed thread idles 3.3-4.6 s now. Helps only where seeds bind (1 node): up to ~1.5 s there, ~0 at 2/4 nodes.
   - Lock granularity: allow 2 mapper calls at once instead of one (a semaphore), or hold the lock only around `hipMemMap`/`hipMemSetAccess`
     (the zero is 0.01 s, create is 0.17 s per chunk). Synchronous mapping already runs 4 calls at once without a crash, and aggregate
     throughput is 1.3-1.6x. Worth up to the level-1 gap (1.4-2.5 s at 2/4 nodes, 0 at 1 node). Risk: more concurrent `hipMemMap` in the
     thread that segfaults; needs a soak (~600 runs for a 1 % event). Not recommended before the segfault question is closed.
   - Reordering the queue (parity-1 halves first, tails last) gives nothing: the lock is work-conserving, the last half completes at the same time.
   - Overlap the plane-pool allocation (4.4-6.8 s) with the arena mapping, now strictly sequential: unknown gain (driver-bound or not),
     needs one ABBA with `ECALC_INIT_TL=1`.

## Decisions for the user
- A. Keep / auto-sync / remove the mapper: recommended keep now, add `BG=auto` (item 2) with the faster mapping; cost of the alternative (BG=0 now): +7-11 s per run (mod), +20 s (m, noisy).
- B. Spend a paired run on BG=0 vs default at 1 and 2 nodes to resolve the model/measurement gap; cost ~1 hold, 2-3 h with the stop rule.
- C. A 600-run soak of default + userfaultfd to learn whether the rc 139 segfault is gone: cost 1 node-day.
