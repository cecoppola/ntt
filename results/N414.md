## A5 — the answer: memory state, not the node. The plane pools get sub-2 MiB pages near the memory edge

**Cause (measured, s24-16).** The dist tier's per-call load (the gather of both operands into the plane pools) and its
transforms (on the plane pools) run 4–10 × slower when the run's device total exceeds the node's free memory in
blocks of ≥ 2 MiB (buddy orders ≥ 9). `rns_init` maps the region arenas first (the seeds stream into them) and the
plane pools **last**, so near the edge the planes are built from what is left: pieces below 2 MiB. The GPU then walks
4 KiB page mappings for every gather and every transform pass over the planes (TLB reach), while the regions' 2 MiB
blocks stay fast. On s24-16 the free memory in ≥ 2 MiB blocks is 447 GB (buddyinfo: 102 + 115 + 113 + 118 GB on
the four NUMA nodes) of 518 GB free; the rest is scattered below 2 MiB and a thread that allocates 420 GB of THP
memory gets 100 % huge pages (the free big blocks are there and movable memory is not the issue). Mid-run
buddyinfo at 1.42 × 10¹¹ shows the ≥ 2 MiB supply exhausted (0–2 GB per node, 19 GB free in all).

| probe (s24-16, `ECALC_PLANE_CAP=2^30 RNS_STRATEGY=C RNS_VERBOSE=1`, first 240 s of the run) | device GB (modelled = measured) | 2³⁰ dist calls in 240 s | load s / call | ntt s / call |
|---|---|---|---|---|
| 1.42 × 10¹¹, default (b1 p1, p2, p3, p4; b2 d1 — five runs) | 501.4 | 55–62 | **0.94–1.04** | 1.15–1.25 |
| 1.42 × 10¹¹, `RNS_PLANES_FIRST=1` (b2 pf1, pf2) | 501.4 | 161–164 | **0.095–0.096** | 0.250 |
| 1.30 × 10¹¹, default (b2 s130) | 464.1 | 117 | 0.513 | 0.697 |
| 1.20 × 10¹¹, default (b2 s120) | 433.1 | 214 | **0.100** | 0.250 |
| 2 × 10¹⁰, default, whole run (b1 s1; 19 calls at 2³⁰) | ≈ 70 | — | 0.06–0.11 | 0.22–0.29 |
| for reference: G13d's C 1.42 × 10¹¹ on s24-16 / P13b's on s24-30 (logs) | 501.4 | — | 0.92 / 0.094 | 1.07 / 0.24 |

So the same node runs the same products at P13b's fast speed (0.095 s) when the planes are mapped first, and at
G13d's slow speed (0.98 s) when they are mapped last; the slowdown grows with how far the device total passes the
≥ 2 MiB supply (433 GB: none, 464 GB: half, 501 GB: full). Not the node: s24-16 is fast at 1.2 × 10¹¹ and with the
switch at 1.42 × 10¹¹. Why P13b's s24-30 run was fast in the default order is not reproduced here (s24-26/30 were
held by P2 for two-node runs); the likely reason is a larger ≥ 2 MiB supply on that node at that moment (the supply
varies with the kernel's own unmovable allocations per NUMA node, e.g. node 0's is the smallest on s24-16) — **assumed**.

Not the cause (measured or read): the page cache (b1: `Cached` 0.4–0.6 GB throughout; the fill step could not write
to the node's root file system, so the cache was never large), THP settings (`transparent_hugepage=always`,
`defrag=madvise`, identical boot line on every run), an alloc/free cycle (four back-to-back 1.42 × 10¹¹ probes and a
420 GB THP touch in between left the load at 0.94–1.04 s), clocks (fclk 2000 MHz, mclk 1300 MHz, perf level auto).
`peer access` time varies 0.75–20 s between runs and does not track the load.

Node properties (s24-16, `~/N414/a5/b1/props_start.txt`): kernel 6.8.0-134, boot line `transparent_hugepage=always
amdttm.pages_limit=134217728 amdttm.page_pool_size=134217728 numa_balancing=disable`, 4 NUMA nodes of 128 GB,
MemTotal 526.6 GB, `HSA_NO_SCRATCH_RECLAIM=1`, amdgpu `noretry=-1`, `svm_default_granularity=9`, no swap.

**Fix**: `RNS_PLANES_FIRST=1` (commit 487458a, `rns_mul.c` `rns_init`, off by default): the plane pools are mapped
before the region arenas, and the seeds start after them. The arenas then take the sub-2 MiB remainder; their
contents are read once per product, so the slowdown there is not seen in the probes.

## A4(b) — `mnrun.sh`'s SHMEM detection (commit 278daf9)

Every word of the command that resolves (`command -v`) to an executable ELF file is checked (`readelf -d` NEEDED,
then `ldd`) for `libsma` / `liboshmem`; the first that links either decides; wrapper options (`-x`) and assignments
(`X=Y`) are skipped; none found: oshmem as before, with a note on stderr. `COMM_SHMEM_IMPL` must be `sos` or `oshmem`
(anything else exits 1). `MNRUN_SHOW_IMPL=1` prints the choice, `=only` prints and exits (test hook).

Tested on aac6 (job 21267, `~/N414/a4_try1/summary.txt`), the SOS build `~/ntt-N414-sos/ecalc/tests/t_comm` and the
OSHMEM build `~/ntt-S13d-osh/ecalc/tests/t_comm`, behind each wrapper: none, `env X=1`, `stdbuf -oL`,
`timeout 600`, `numactl --interleave=all`, `nice -n 0`, `setarch x86_64 -L`, and all of `env stdbuf timeout numactl`
chained — **sos and oshmem detected correctly in all 16 cases**; `bash -c ./tests/t_comm` → sos (the path word
resolves); `COMM_SHMEM_IMPL=bogus` → refused. The four real launches through the wrappers reached SOS's
`shmem_init` / `shmem_malloc` on both PEs (the SOS launch form); they then failed on the 8 GiB pool because the batch
exported `COMM_SHMEM_DEVHEAP=1`, which `t_comm` (no HIP) cannot use. Rerun without it (job 21282, 2 nodes, and 21283,
3 nodes, table above): every wrapped launch VERIFY OK. (Before the change, a wrapper word made `mnrun.sh` pick OSHMEM's
`--mpi=pmix` + `setarch -L` form for the SOS binary — S13d §3.1's failed 3-node launch.)
