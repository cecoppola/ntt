# RL15 — concurrent VMM remaps in the block pool (`DB_POOL_VMM_PAR`, `DB_POOL_VMM_EXTEND`; Phase 15, PLAN §36)

Agent RL, branch `p15-RL` from `main` 7367e25 (B0). aac6 clone `~/ntt-RL15`, logs `~/RL15/s1`, `s2`, `s3` (one directory per

## 0. Summary

- **Concurrent remaps do not help: the HIP runtime serializes the VMM calls across devices** (measured). With the global pool
  lock dropped and the four quarters served by four threads, four remaps of 11 × 2 GiB chunks finish at 0.50, 1.00, 1.49, 1.98 s
  (unit test, 44 GiB arenas) — the same 1.98 s as the serial path (4 × 0.50). At 10¹¹ the same: three remaps complete at 0.47,
  0.97, 1.45 s either way; `dm` off 99.25 / 99.29 / 99.91 s, on 99.48 / 99.73 s (measured, default S). T2's modelled −1…−2.8 s
  does not exist with this driver.
- **What the remap costs is `hipMemSetAccess`, ≈ 0.021 s/GiB, proportional to bytes** (measured: 0.46–0.50 s for 22 GiB;
  unmap 0.008–0.04 s, map 0.000–0.003 s when not queued; the same 0.02 s/GiB with 4 GiB chunks). In the concurrent runs the
  queued thread waits in whichever call comes next (unmap, map or access), so the lock is process-wide inside the runtime, not
  one call's.
- The only lever left inside `dbig.c` is **moving fewer bytes**: `DB_POOL_VMM_EXTEND=1` (new, off) extends the free extent that
  needs the fewest chunks moved (at its end or front into empty VA slots) instead of building a fresh run. Result: §4.
- **A hang** (not in the changed code path): one run of the scratch build (B0 + p15-T2 + this branch, `BS_SEED_FILL=128`,
  both switches off) stopped after init with every thread in `futex_wait` (§5). Reported for the integrator.

## 1. The problem (T2, results/T215.md §4 on `p15-T2`)

With `DB_POOL_VMM=1` (the default) a block request that finds no contiguous free extent is satisfied by `vmm_make_room`: the
wholly free 2 GiB chunks are unmapped and mapped again contiguously. At 10¹¹ the division's two 22.22 GB blocks per APU (t, then
xq) remap on three or four APUs, and those remaps queue: T2 measured 1.84 s before the first product at S = 168.

Two things in the code serialize them, not one:
1. `vmm_make_room` runs with the **global** pool lock `g_pool_mx` held across its HIP calls;
2. `db_reserve` allocates the four quarters **in a loop on one thread** (`for d: q_alloc(d, …)`), so even with a per-device lock
   APU 1's remap would not start before APU 0's returned.

Both are changed under `DB_POOL_VMM_PAR`; the measurement then showed a third, in the runtime, that cannot be changed here.

## 2. Design (`ecalc/dbig.c`)

### `DB_POOL_VMM_PAR=1` (default 0)

- **`vmm_make_room_par`** (in place of `vmm_make_room`). Under `g_pool_mx`: wait for the background mapper (as before), pick
  the wholly free chunks (same scan) and the target run (the lowest run of `m` slots empty once those chunks are unmapped — the
  slot the old code finds after unmapping), take the chunks out of the extents, set the device's `busy` flag, **drop the lock**.
  Outside it: `hipMemUnmap` of the moved chunks, `hipMemCreate` of any growth chunks, `hipMemMap` + `hipMemSetAccess` at the
  target (`vmm_hip_run` = `vmm_map_run` without the slot table and counters). Re-lock: slot table `h[]` updated in one step (old
  slots 0, new slots set), growth/remap counters, `busy` cleared + broadcast, the new extent inserted; the caller's `ext_take`
  follows in the same critical section. When the VA has no room nothing is touched (the old code unmapped and remapped the
  chunks back: same result, return 0).
- **`q_alloc_locked`**: a failed `ext_take` on a device whose remap is in flight (`busy`) waits on the pool's condition variable
  and retries before remapping itself (two remaps of one device never overlap).
- **`db_reserve_par`**: the four quarters are first taken without a remap in one critical section (exactly `ext_take` +
  `live_add` per device); the devices that failed are served by one thread each when there are ≥ 2 of them, else inline.
  Per-device pools and `ext_take` read no other device's state, so every quarter lands where the serial loop puts it: **the same
  layout** (the 10¹¹ remap lines are identical in slot and chunk count off/on).
- The verbose remap line gains `(concurrent: HIP calls x s = unmap + map + access)`.

### `DB_POOL_VMM_EXTEND=1` (default 0; uses the lock-dropping remap, with or without `PAR`)

Before building a fresh run of ⌈need / C⌉ chunks, look at every free extent of the arena: an extent of b bytes needs
x = ⌈(need − b) / C⌉ more chunks; if its end (or its front) is chunk-aligned and the x slots after (before) it are empty, and at
least x wholly free chunks lie outside it (never more growth than the default), it is a candidate; the one with the fewest x
wins if x < ⌈need / C⌉. Those x chunks move next to it and the merged extent serves the request. SetAccess cost is per byte, so
the saving is (⌈need / C⌉ − x) × C × 0.021 s/GiB. A different placement than the default (hence a switch); the digits cannot
depend on addresses.

### Thread-safety review (what is shared across devices)

| state | shared? | under the switches |
|---|---|---|
| `g_ext[d]` (free extents) | per device; every access under `g_pool_mx` | the moved chunks leave the extents before the lock is dropped, the new extent enters after it is retaken; the target slots are empty (or among the moved chunks), so no other request — same device, other device, the background freer — can reach that VA meanwhile |
| `g_live[]`, `g_nlive`, `g_live_bytes[]`, peaks | **one global table** | only under the lock (`live_add` in `q_alloc_locked` and `db_reserve_par`) |
| `g_donated[]`, `g_ndonated`, `g_pool_bytes` | global | only under the lock (the hipMalloc fallback, as before) |
| `g_vmm[d].h[]` (slot table) | per device, read by `db_acct` (mem_report, the budget check) for **all** devices | written only under the lock, after the HIP calls, in one step: mem_report counts the chunks either before or after the remap (the same count; growth chunks after), never half. Checked by the unit test (mem_report each round; live + free exact) |
| `g_vmm[d]` counters | per device | under the lock |
| `g_vmm_cv` | one condition variable | broadcasts also wake the background-mapper waiters; every waiter re-checks its predicate in a loop |
| `g_tail[d]`, `g_pack_large`, `g_pin_tail` | tail per device; flags global | the flags are set by the driver thread around `db_reserve`, only read by the worker threads |
| `mem_dev_note` (mem.c registry) | global (`omp critical(memreg)`) | not touched by a remap: the arena's VA range is fixed and noted once in binsplit.c; the remap changes which slots are mapped, which only `db_acct` reports (mem.c's `gather` subtracts the pool's borrowed bytes from the noted range, unchanged) |

**HIP VMM calls on different devices concurrently**: safe (the runtime API is thread-safe; the ranges are disjoint, one
reservation per APU; 10¹¹ identical, unit test and stress pass), but **not concurrent**: the runtime runs them one at a time
(§3.1). The existing `g_vmm_map_mx` comment (the background mappers kept one at a time because four "hold the runtime's lock
while blocked on each other") is the same lock seen from the other side. The remap never overlaps the background mapper
(`vmm_make_room*` waits for it to finish first).

The unit test `tests/t_vmm_par` (new): per APU a VMM arena (`db_vmm_arena_alloc` + `db_donate_adjacent`, as binsplit.c does)
plus a 64 MiB donated region; every round the arena is filled with chunk-sized blocks carrying a byte pattern, every other one
freed, and **one `db_reserve` of half the arena per quarter forces a remap on all four APUs at once**; a background thread
allocates / writes / checks / frees 1 MiB blocks on every APU the whole time (they come from the small region, so the lock being
dropped is exercised without touching the chunks). Checks per round: the kept blocks' patterns survive, the new quarters lie in
their APU's VA range and read back, one remap per APU and no growth, the chunks moved, live + free = arena + region exactly with
the arena fully live and no hipMalloc (under a lock that pauses the background thread), `mem_report` printed; at the end every
byte back and the background blocks all correct (0 bad of 47 000–454 000).

`T_VMM_TOP=1` also frees the top two blocks (a 2-chunk free extent at the arena's end with empty slots above): with
`DB_POOL_VMM_EXTEND=1` the test requires 2 chunks fewer moved in round 0, without it k/2 (§4).

## 5. The hang (f0b, job 21530, 2026-09-27 12:07–12:23 EDT)

Scratch build 6230345's predecessor 4b09f37 (B0 + p15-T2 + p15-RL at e5a2946), `BS_SEED_FILL=128 DB_POOL_VERBOSE=1`, **both
RL switches off** (the code path is B0's: `vmm_make_room` under the global lock, the serial quarter loop). The run printed init
and the budget check, then nothing for 15 min: the next line should have been `bs: seeds were computed during init` and the
background mapper's `mapped chunks 0..38` line. 199 threads, all `S` in `futex_wait_queue`, 0 % CPU (`/proc/<pid>/task/*/wchan`);
gdb cannot attach (ptrace_scope), SIGABRT left no core (apport). The same setting ran normally twice before and after (f0a, and
f1a/f1b with PAR). A user-space deadlock between init's end and bs's start — the seed thread, the VMM background mappers
(`vmm_bg_map`: `g_vmm_map_mx` held across `vmm_map_run` + `hipMemsetAsync` + `hipStreamSynchronize`), `db_vmm_arena_wait`
(pool lock + condition variable) and the runtime's own lock are the candidates. Not reproduced yet (f0c in job 21542 repeats it).

## Open issues

- The hang (§5): once in 5 fill-128 runs here; unknown whether B0 alone can hit it (T2's runs are the larger sample).
- `DB_POOL_VMM_PAR`: correct and safe but no gain with this ROCm (the runtime serializes the VMM calls). Keep off; it would
  matter only with a runtime that maps devices concurrently. Recommendation: do not adopt.
- The real levers are outside `dbig.c`: fewer remaps (T2's other suggestion: APUs 1–3's arenas one chunk larger, as APU 0's is —
  binsplit.c's sizing) or remaps overlapped with GPU work ahead of the request (a hint from newton_db.c before the division's
  products, on a helper thread — it would still hold the runtime's lock, so launches from other threads would queue behind it).
- Outside my files: `ecalc/Makefile` (one target and the TESTS list for `tests/t_vmm_par`).
