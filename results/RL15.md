## 1. The problem (T2, results/T215.md §4 on `p15-T2`)

With `DB_POOL_VMM=1` (the default) a block request that finds no contiguous free extent is satisfied by `vmm_make_room`:
the wholly free 2 GiB chunks are unmapped and mapped again contiguously (0.45–0.49 s for 11 chunks at 10¹¹, measured by T2).
At 10¹¹ the division's two 22.22 GB blocks per APU (t, then xq) remap on all four APUs when the reserved tail is gone
(S = 168, `BS_SEED_FILL=128`), and those remaps queue: 1.84 s before the first product (measured +1.97 s in "A mu + shift").

Two things serialize them, not one:
1. `vmm_make_room` runs with the **global** pool lock `g_pool_mx` held across its HIP calls;
2. `db_reserve` allocates the four quarters **in a loop on one thread** (`for d: q_alloc(d, …)`), so even with a per-device
   lock APU 1's remap would not start before APU 0's returned.

A per-device lock alone would therefore gain nothing; both are changed under the switch.

## 2. Design (`ecalc/dbig.c`, switch `DB_POOL_VMM_PAR`, default 0)

- **`vmm_make_room_par`** (replaces `vmm_make_room` when the switch is on). Under `g_pool_mx`: wait for the background
  mapper (as before), pick the wholly free chunks (same scan) and the target run (the lowest run of `m` slots that are empty
  once those chunks are unmapped — the same slot the old code finds after unmapping), take the chunks out of the extents,
  set the device's `busy` flag, **drop the lock**. Outside it: `hipMemUnmap` of the moved chunks, `hipMemCreate` of any
  growth chunks, `hipMemMap` + `hipMemSetAccess` at the target (`vmm_hip_run`: `vmm_map_run` without the slot table and
  counters). Re-lock: update the slot table `h[]` in one step (old slots 0, new slots set), the growth/remap counters, clear
  `busy` + broadcast, insert the new extent; the caller's `ext_take` follows in the same critical section. When the VA has
  no room nothing is touched (the old code unmapped and remapped the chunks back: same result, return 0).
- **`q_alloc_locked`**: with the switch, a failed `ext_take` on a device whose remap is in flight (`busy`) waits on the
  pool's condition variable and retries before remapping itself (a second remap of the same device never overlaps the first).
- **`db_reserve_par`**: the four quarters are first taken without a remap in one critical section (exactly `ext_take` +
  `live_add` per device, as the serial loop); the devices that failed (need a remap or a hipMalloc) are served by one
  thread each when there are ≥ 2 of them (`q_alloc` on each), else inline. Per-device pools and `ext_take` read no other
  device's state (the global `g_pack_large` / `g_pin_tail` flags are only read), so every quarter lands where the serial
  loop puts it: **the same layout**, hence the same timing structure otherwise and the same digits.

### Thread-safety review (what is shared across devices)

| state | shared? | under the switch |
|---|---|---|
| `g_ext[d]` (free extents) | per device, but every access under `g_pool_mx` | the moved chunks leave the extents before the lock is dropped; the new extent enters after it is retaken; the target slots are empty or among the moved chunks, so no other request (same or other device, the background freer) can reach that VA meanwhile |
| `g_live[]`, `g_nlive`, `g_live_bytes[]`, peaks | **global table** | touched only under the lock (`live_add` in `q_alloc_locked` / `db_reserve_par`) |
| `g_donated[]`, `g_ndonated`, `g_pool_bytes` | global | only under the lock (hipMalloc fallback, as before) |
| `g_vmm[d].h[]` (slot table) | per device; read by `db_acct` (mem_report, the budget) for **all** devices | written only under the lock, after the HIP calls, in one step: mem_report counts the chunks mapped either before or after the remap (same count; growth chunks after), never half |
| `g_vmm[d]` counters (`n_remap`, `remap_chunks`, `t_remap`, `n_grow`, `grow_chunks`) | per device | updated under the lock |
| `g_vmm_cv` | global condition variable | broadcasts wake the background-mapper waiters too; every waiter re-checks its predicate in a loop |
| `g_tail[d]`, `g_pack_large`, `g_pin_tail` | tail per device; flags global | the flags are set by the (single) driver thread around `db_reserve` calls, only read by the worker threads |
| `mem_dev_note` (mem.c registry) | global (`omp critical(memreg)`) | not called by the remap: the arena's VA range is fixed and noted once in binsplit.c; the remap changes which slots are mapped, which only `db_acct` reports |

**HIP VMM calls on different devices concurrently**: the HIP runtime API is thread-safe; `hipMemUnmap`/`Map`/`SetAccess`
here act on disjoint VA ranges (one reservation per APU). Whether the driver actually overlaps them is measured below
(§3, the unit test's time for four remaps serial vs concurrent). The existing comment on `g_vmm_map_mx` (the background
mappers are kept one at a time) records that four concurrent *first-time* mappers (which also zero pages) contended in the
driver; the remap moves existing physical chunks (no create, no zeroing), and the background mapper has always finished
before a remap starts (`vmm_make_room*` waits for it), so the two never overlap.
