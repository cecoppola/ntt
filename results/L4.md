# L4: refit of the time model to all of 2026-10-11's multi-node aac7 runs; what it got wrong and why (wave L, agent L4)

Date 2026-10-11 (Eastern). Base main a1569d5, branch `l4` (worktree `../ntt-wt-l4`). CPU only: local analysis plus the aac6 MI250 CPU nodes for the schedule search; no aac7 job (ssh reads of logs only).
Labels: **measured** = parsed from run logs (`total`, stage times, xstats); **modelled** = `ecalc/mn_model.py` / `estimate.py` / statistics on measured values; **assumed** = the target fabric (100 GB/s per APU, 2 us) and the part-file rate, as in every standing estimate.
Files: `ecalc/mn_model.py`, `ecalc/estimate.py`, `ecalc/refit_s48.py` (`--l4`), `ecalc/aac7_l4_fit.json` (new), `tools/groups_table.py` (`GT_PROFILE`, `GT_RELEASE_GB`), `archive/drivers/l4/l4_search.sh`, this file. The run table is `archive/results-raw/L4_runs.tsv` (137 rows).

## 0. Answer in short
1. **Two things were wrong in the model, one was a bookkeeping bug.**
   - **Bug (fixed, affects every uneven MN_GROUPS result):** a tree level was costed through its *last* (clipped, smaller) group. The real level ends when its slowest group ends, and with an uneven last group that is a full-size group. The "model-best" forms of C09 (`2,4,8,16,80,560,576`: 146.5 s) rest on this: with the level costed at its slowest group the same form is 196.2 s, 12.5 s *worse* than the standing default `2,4,8,16,32,64,192,576` (183.7 s). Evenly dividing schedules (all of B04's, the 576 default) are unchanged. Behind the switch `MN_MODEL_TREE_TOPONLY=1` (old behaviour).
   - **Rate (refit):** the layv factor 0.655 was fitted on the 6-node default `2,6` alone, the one 6-node schedule that is unusually slow. Fitted on every non-power-of-2 class it is **0.83** (C02's span-based 0.73-0.86), and the bulk rate depends on the NIC launch group: **10.60 GB/s per APU thread in the fast group B, x0.815 in the slow group A** (the S48 single 10.31 was a mix of the two).
2. **Residuals** (rms of log(model/measured) over 15 run classes): before 0.156, after 0.108; power-of-2 classes -11..+5 % before, -3..+3 % after (mode-adjusted); 3 nodes +18 % -> +2 %; 5 nodes +7..+40 % -> +10..+19 % (group B; the old fit was mode-blind); 6 nodes -13..+33 % -> -25..+13 %. Not closed: the 5-node order (default measured fastest, model flat) and the 6-node default `2,6` (measured 278-336 s, model 252 s) are still wrong (section 3).
3. **576 nodes (modelled, fabric assumed):** the standing default schedule `2,4,8,16,32,64,192,576` moves 183.7 -> 178.2 s no-write at 3.71e13 (layv 0.655 -> 0.832); the best schedule moves from the unmeasured `80/560` forms (146.5 s) to forms within 0.2 s of the default (section 4). The ~19 s "round down to 569" and the 13-21 % "model-best" advantage of C09 are artefacts of the bug, not savings.

**2.1 Bytes per node, model vs measured (GB per node; measured = sum of xstats kinds, S48/C09/f3 logs).**

The measured `bs` also holds the leaf's redistributions; the model's tree is the levels only. The 2-node level is under-counted by about 20 % (operand redist / result / spill kinds), the 6-way single level over-counted by 15 %.

**2.2 Critical path of a level (the bug).** `tree_cost` used `level_top_group(..., 'top')`: the group holding the last node. For `MN_GROUPS=4,5` that is a 1-node group (cost 0) and level 4 cost nothing; for `2,4,8,16,80,560,576` the level of 80 was costed as a 16-node group and the level of 560 as one child. Measured per-node level timers (`mn: node N level L [..) in X s`): `4,5` level 1 = 42.9-45.7 s on nodes 0-3 and level 2 = 15.6 s on every node, while node 4 (not in a 4-node group) shows 57.0 s for level 2 because it waits for the 4-node level first (critical path = the full group, then the top level; tree 61.3 s measured). Fix: a level costs `max(top group, last full group)` (`mn_model.tree_cost`, `TREE_CRIT`). Changes nothing when S divides g.
**2.3 Rate per kind (xstats, measured, GB/s per APU thread = GB / t_post).** layeq 16.0 / 18.4 (2 / 4 n, fast); layv 8.2-9.3 at 6 n (t_post double counts the INTER2 overlap, C02: span rate 13.3-15.7); the other kinds are slow and fall with group size: redist 8.9 / 6.0 / 4.6, result 10.6 / 8.9 / 7.0 (2 / 4 / 6 n), addsh 9-10; they carry 29-38 % of the exchange time but 15-20 % of the bytes. A `k_other` rate factor for them (new hook in `Fabric`, default 1.0) was tested at 1.0, 0.8, 0.6, 0.45 with bw refit each time: the totals' rms is 0.124-0.126 for all of them (no information in the totals), so it stays 1.0.
**2.4 Per-exchange fixed cost.** The per-message latency moves the walls < 0.5 % over 2-68 us (S48); not identifiable from totals; unchanged (8.5 us).
**2.5 Level structure vs measured tree time x r** (tree volume in GB/s x s, measured; the tree timer also holds up to ~10 s of waiting for the slowest leaf, so read differences, not levels):
single level `[3]` 492, `[4]` 505-542, `[5]` 488, `[6]` 551-579; two levels `[2,4]` 528-578, `[2,5]` 590, `[4,5]` 587, `[3,6]` 630, `[2,6]` 607-855. A single k-way level costs about the same for k = 3..6 (the model's fold grows it with k; its volume is within 15 %). Rate-adjusted (total = a + b / r with a, b from the two group-B/C09 `[6]` points: a 126 s, b 1024 GB/s x s) the **6-node default `[2,6]` is +24..+33 s slower than `[6]`** (f3 pair +33, S48 +24 / +25, C09 r1_A +66 with a 52-s straggler pair) and `[3,6]` +14 s; the model says `[2,6]` is 10 s *faster*. At 5 nodes the raw gaps (`[2,5]` +13 s, `[4,5]` +19 s vs `[5]`) are inside what the rates alone explain (B06: 9.6 vs 10.3 GB/s), so the 5-node order is **not established** (one run per schedule) and the model's flat order is not contradicted. At 4 n `[2,4]` vs `[4]` is 0 (f3 fast pair 183.0 vs 181.3 s). Per-node timers show where `[2,6]` loses: level 1 is three independent 2-node products whose times differ by up to 2x within a run (14.7 / 30.2 / 18.1 s; 14.1 / 16.3 / 51.7 s in C09 r1_A) and level 2 waits for the slowest pair: the cost is an expected maximum over groups, not a mean. That term is **not modelled** (unidentified, 3.3).

**3.2 What is fixed and what is not.** Fixed: 3 n (+18 -> +2 %), the 4 n slow/fast modes by group (-11 / +2 -> -1 / +0 %), 5 n over-prediction roughly halved (+40 -> +19 % default), 6 n `[6]` and `[3,6]` (+19..+33 -> +1..+13 %). Not fixed: (a) the 6-node default `[2,6]`: measured 278-336 s, model 252 s (B) / 291 s (A); it got *worse* on the S48 runs the old profile was fitted to (+2 -> -10 %) because the layv factor rose; and the 6-node order (measured `[6]` 232-260 <= `[3,6]` 264 < `[2,6]`, rate-adjusted 3.2; model `[2,6]` < `[6]` ~ `[3,6]`); (b) the 5-node class is still +10..+19 % high in group B (it needs either a higher layv factor or group B at ~12 GB/s; 5 n has one run per schedule and an unknown group); the 5-node order is within rate noise (2.5) and the model's flat order agrees.
**3.3 A level penalty was tried and rejected.** A multiplier on tree levels whose group is not a power of two and whose children are multi-node (`MN_MODEL_MIX_PEN`, default 0) lowers the residual monotonically (rms 0.108 -> 0.084 at 0.6, the edge of the scan) while the layv factor rises to compensate (0.83 -> 0.93): the two are not separable with 5 and 6 nodes (two to four runs per class). It is kept as a sensitivity (`MN_MODEL_MIX_PEN`), not adopted.
