- **Live conclusions:** (1) a tree level costs its slowest group, so explicit `MN_GROUPS` balanced tops (`2,4,8,16,64,192,576`, or `2,4,8,40,200,N`, `5,35,140,N`, `4,24,96,N` for N < 576) are 0-25 s better than the standing form and the code's default schedule is far worse at almost every N != 576 (8 s to 2000 s): any node exclusion needs an explicit `MN_GROUPS`; at 576 the standing `2,4,8,16,32,64,192,576` is within 0.2 s of the best. (2) Non-power-of-2 groups run the slower `layv` kind (rate x0.92 of layeq in the model, raw per-thread ratio 0.41). (3) The 4-node bimodality (fast 181 s, slow 208 s) is the NIC launch group (rate x0.82). (4) The 6-node default `[2,6]` is slower and more variable than the model (+23 +- 12 s vs `[6]`), unexplained. (5) Fabric at 576 is not the bottleneck if 100 GB/s per APU holds (exposed communication 13-19 % of the wall); distributed tree levels are 33-40 %; the injection bandwidth per APU is the one input that moves the wall by more than +-20 s.
- **Steps in wall time at 576** (D213d, modelled): the term layout gives the top node 1.036 x the average digits, so the wall steps at 4.29 -> 4.30e13 (+13 % for 1.2 % digits); the model matches the C plan at 401/401 sizes. ## L4 — refit of the time model to all of 2026-10-11's multi-node aac7 runs; what it got wrong and why (wave L, agent L4)

Date 2026-10-11 (Eastern); base main a1569d5, branch `l4`; CPU only (local analysis plus aac6 CPU nodes for the schedule search; no aac7 job). Files: `ecalc/mn_model.py`, `ecalc/estimate.py`, `ecalc/refit_s48.py` (`--l4`), `ecalc/aac7_l4_fit.json`, `tools/groups_table.py` (`GT_PROFILE`, `GT_RELEASE_GB`, `GT_LAYV`), `archive:drivers/l4/l4_search.sh`; run table `archive:results-raw/L4_runs.tsv` (148 rows), refit output `archive:results-raw/L4_refit.out`, searches `archive:results-raw/L4_groups/`. Labels: measured = parsed from run logs; modelled = `mn_model.py` / `estimate.py`; assumed = the target fabric (100 GB/s per APU, 2 us) and the part-file rate.

**Answer.** One bookkeeping bug and one mis-fitted rate explain the misses; a third effect (the 6-node default's variance) is not modelled.
- **Bug (fixed, affects every uneven `MN_GROUPS` result):** a tree level was costed through its last (clipped, smaller) group; the real level ends when its slowest group ends. C09's "model-best" forms (`2,4,8,16,80,560,576`: 146.5 s) rest on this: costed at the slowest group the same form is 196.2 s, 12.5 s worse than the standing default `2,4,8,16,32,64,192,576` (183.7 s). Schedules whose levels divide the node count are unchanged (bit-identical outputs). Old behaviour behind `MN_MODEL_TREE_TOPONLY=1`.
- **Rate (refit):** the layv factor 0.655 was fitted on the 6-node default `2,6` alone; fitted on all non-power-of-2 classes (3, 5, 6 nodes, 7 schedules) it is **0.92** (assumes the unknown NIC launch group is the fast one B; 0.73 / 1.0 move the 576 estimate by +-3 s). The bulk rate depends on the NIC launch group: **10.63 GB/s per APU thread in B, x0.818 in A** (S48's 10.31 was a mix).
- **Not modelled:** 6-node `[2,6]` is slower on average (256-277 s vs 243 s for `[6]`) and more variable (223-336 s, sd 22 s vs 10 s) than the model's 240 s; per-node timers show one 2-node group of three occasionally taking 2x as long (an expected maximum over groups). Unidentified with 5-7 runs per class.
- **Residuals** (rms of log ratio over 12 run classes): 0.156 -> **0.062** (group B for classes of unknown group). Power-of-2 classes -11..+5 % -> -3..+3 %; 3 nodes +18 -> -3 %; 5 nodes +7..+40 -> +5..+12 %; 6 nodes `[6]` +27 -> +2 %, `[3,6]` +17 -> -6 %, `[2,6]` +6 -> -13 % (worse).
