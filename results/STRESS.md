# STRESS — forced VMM remaps of the dbig block pool, with the CRT/VERIFY checks on (C2)

**Question.** At 3.7e13 digits and above, target runs failed (CRT flags = wrong transform-domain values; T1/VERIFY failures = wrong in-range limbs), more often the larger the run. One software lead is the block pool's free and VMM remap path (`q_free`, `vmm_make_room` in `ecalc/dbig.c`; audit in `POOLRACE.md`: 0 unsafe, 1 unclear = the remap unmap). No setting had ever made a remap happen on aac7 (0 in 26 pressure runs). Can a harness make remaps happen many times, with the diagnostics on, and show a flag, a VERIFY failure or a digit difference? Also (Q140 item 3): per-run NIC deltas with real 2-node traffic.

**Change / branch.** Branch `stress`. Switch `DB_POOL_FORCE_REMAP=<n>` (default 0 = off; registry, `ecalc/README.md` row, review date 2026-11-30): every n-th pool allocation or free on a device runs a forced remap: up to max(64, request chunks) of the highest wholly free VMM chunks are unmapped and mapped again, in reverse order, into the lowest run of empty slots (no growth, only free memory moves; after a free the freed block's chunks are among those that move). With `DB_POOL_VMM_CHUNK_GB=0.015625` (16 MiB instead of 2 GiB) the arena has thousands of chunks to move. Driver `tools/stress/stress.sh`, summary `tools/stress/summarize.py`.

**Method.** aac7, path 1 (libfabric), the aac7 launch line, `DB_POOL_VERBOSE=1` (prints the remap counts at the end), `DB_POOL_FORCE_REMAP=1`, 16 MiB chunks. Arms = knob off/on (k0/k1) x `DB_FREE_SYNC` 0/1 (s) x diagnostic words off/on (d1 = `P24_CHECK=2 COMM_SEQ_CHECK=1 XSHMEM_ROUND_STATS=1`) x rounds default/tiny (r1 = `XSHMEM_ROUND_MB=2`, a 2-node pair then moves in chunks of about 0.3 MiB; the target's pairs are 233 KB). Runs go round by round; any anomaly keeps the log and stops the arm. Each run: rc, VERIFY OK, CRT flag (`P24 CRT flag` fatal), P24_CHECK flag count, remaps (from the pool's release line, summed over APUs and processes), digits (sha256 of the unpacked output against the sha256 of the first D digits of the 1e11 reference), wall time. Items: 1 node 2e10 digits x 8 arms (s=0 and s=1 separately), 2 nodes 2e10 digits (digits checked), 2 nodes 6e10 digits (no digit file: VERIFY and flags only). Sizes chosen from the planner (`plan_values.py --fit`): 1 node 2e10 = 213 GB per node, 2 nodes 6e10 = 275 GB per node, against 444 GB.

**Results (all measured, aac7, 2026-11-01).**

Knob proof (1 node): 1e9 digits, n=1: 28 remaps per APU (about 1000-1800 chunks moved per APU), VERIFY OK, digits identical; 4e9 digits: 112 remaps per run, identical. Remaps per run are about 30 per APU at 1 node whatever the size (the number of pool allocations and frees of the division phase); at 2 nodes with the diagnostics and 16 MiB chunks a 2e10 run does about 11,000 and a 6e10 run about 12,300 (all APUs and processes).

Gates for the knob: 1 node, 1e9 digits, knob off and on (three builds, the last on the tree merged with main 1250160c): PASS, VERIFY OK, digits identical. 2 nodes, 1e9 digits: off PASS (12.1 s ecalc), on (n=1, 16 MiB chunks) PASS (118 s: the remaps cost 21-45 s per APU there), P24 in use. `switch_registry --check` rc 0, doccheck rc 0 (see RESUME). Unit tests with the knob on, 1 node: `t_dbig 0` VERIFY OK (555 checks), `t_newton 20` VERIFY OK (2752 checks).

Why fewer runs than planned: every item had a start-time cap (60 min at 1 node, 85 min at 2 nodes, so each item stayed within about 2 h) and no run was stopped by an anomaly. Runs with the knob on are slow, so the cap was reached: 1 node about 105 s (knob off) vs 120 s (on); 2 nodes at 2e10 about 75 s (off) vs 410-420 s (on, 5.5 times: the forced remaps of the 16 MiB chunks cost 21-45 s per APU per run); at 6e10 about 75 s vs 470-520 s. The 2-node 2e10 item therefore did one repetition of 14 arms (arms k1s1d1r0 and k1s1d1r1 and the whole second repetition did not start); the 1-node items did 1-2 of 3 repetitions in the arms' round order (the last arms of the final round are missing). The d and r letters change nothing at 1 node (no P24, no exchange rounds there).

NIC delta (Q140 item 3; the kit's `rl_nicdiff` of `remote/run/lib.sh` on `nodesnap.sh` snapshots before and after the first 2-node run, arm k0s0d0r0, 2e10 digits, 2 nodes, 8 NICs listed per node; measured, bytes estimated from the packet-size buckets, mean per node, spans the snapshot interval and the run): tx 517.8 GB and rx 517.8 GB per node; error-like counts 334 per node (mean), paused counts 911,126 per node. Top-5 by FEC + drops: node A `fec=752 pause=10665 stall=6.97e9 drop=8`, node B `fec=554 pause=10960 stall=6.71e9 drop=7` (the kit's columns: FEC codewords/lane errors, pause events, link-layer-retry stalls, drops). Per NIC (cxi0 of node A): 82.58e6 packets sent, 82.58e6 received, error-like 190, FEC 376, drops 2. So the deltas show real traffic and small FEC/drop counts on all NICs; no run was affected (digits identical). The full per-NIC table is in the run's `nic.txt` on the cluster.

**Verdict.** Flags not reproduced; a software cause is not shown at this scale. The harness made the remap path run 166,332 times in 59 runs (about 30 forced remaps per APU per 1-node run, about 1,500 per APU per 2-node run), at 1 node 2e10 and 2 nodes 2e10 / 6e10 digits, with `DB_FREE_SYNC` 0/1, the P24/sequence/round diagnostics and tiny exchange rounds, with 0 CRT flags, 0 P24_CHECK flags, 0 VERIFY failures and 0 digit differences in the 43 runs whose digits were compared (the 16 runs at 6e10 are VERIFY-checked only). Limits: the target's sizes (3.7e13 digits, 576 nodes, 2304 PEs, 233 KB pairs on a real fabric) are 600 times larger and the pool's remaps there are in the real memory-pressure regime, which no aac7 setting reaches; the forced remaps move only free chunks and the chunks are 16 MiB, not 2 GiB; one repetition per 2-node arm is too few to see a rare event (a 0.1-per-run failure rate would have a 90 % chance to show in about 22 runs of the same kind; assumed, if the cause were reproduced by this stress). The remap path itself (hipMemUnmap / hipMemMap / hipMemSetAccess, 166,332 times) ran without an error.

**Open issues.** (1) The hardware lead (two target nodes with uncorrectable HBM errors) is untouched by this work. (2) The knob raises the run time 5-6 times at 2 nodes; a cheaper variant (fewer chunks moved per event) would allow more repetitions. (3) No repetition 2 at 2 nodes; no 6-node arm (aac7 has 2 usable NIC nodes).

**RESUME.** Branch `stress` on origin, merged with main at the last step; the gate items and stress items are finished and no job is left.
