## 1. What the item asks, and what the code actually transposes

TARGET_HW_REVIEW §3 item 5 proposes tiling "the NTT's transposes (16 % of the multiply, measured aac6)" to the Infinity
Cache's 16–64 MB sweet spot (the target report's 1.3× over HBM streaming for working sets of that size). Reading the code
first:

* **The 16 % figure is bench/13's (RESULTS §14, Phase 2).** That multiply was an explicit four-step with two transposes
  per transform. The production single-APU NTT (`ecalc/ntt.c`, the paper's tiled single-transform NTT, Phase 8 on) has
  **no transpose kernel**: its b16 passes work in place at row stride 2^s_lo. The IC-residency idea for those passes was
  built and measured in Phase 13a K as `NTT_MALL` (passes of narrower span run chunk by chunk to completion): **no gain,
  ±2 %, rejected** (RESULTS §79 table). So at size 1 and below 2³⁰ points, item 5 has no kernel to apply to.
* The transposes that remain on the one-node 10¹¹ path are in the **four-APU four-step** (`rns_dist.c`, planes of ≥ 2³⁰
  points split over the four APUs by xGMI; `rns_mul_dist` and `rns_mul_dist_mn`):
  1. `k_transpose` (rns_dist.c:95; called at :845 and :1708): each prime plane rows × C → C × rows into the scratch
     `xt`, then `hipMemcpyAsync` back — 4 planes per product, each 16 B/point for the transpose + 16 B/point for the
     copy. Already a 32 × 32 LDS tile, block (32, 8), tiles in row-band order.
  2. the twiddled packs / unpacks around the all-to-all (`ntt_dist.c` `k_twpack` / `k_unpacktw`, `rns_dist.c`
     `k_twpack_g[r]` / `k_unpacktw_g[r]`): 32 × 32 LDS tiles fused with the twiddle, measured in Phase 13b X and
     Phase 15 G5 at 1.2–1.6 TB/s against a 3.1–3.4 TB/s device copy; the untwiddled `k_unpack_g` / `k_pack_cols_g`
     at 2.3–3.2 TB/s ("not worth touching", G515).
  3. the untiled gathers `k_gather` / `k_gather_mn` (coalesced read, strided write at 8 B granularity) that build the
     row layout from the limb sequence, and `k_scatter_runs` (coalesced both sides).
* **A transpose has no data reuse**: every byte is read once and written once, so the IC's 1.3× for a re-read 16–64 MB
  working set cannot apply as such. What a 16–64 MB "supertile" order can change is the access granularity on the
  strided side (8 KB contiguous runs per destination row instead of 256 B) and the DRAM page locality, i.e. how close
  the transpose gets to the copy rate. Phase 13b X already measured the tiled packs at 75–90 % of the copy rate, so the
  **upper bound for any transpose kernel change is the gap to the copy rate** (≤ 10–25 %), and the larger lever on path
  1 is the copy back (an equal second plane pass), which no kernel tiling removes.

Shapes at 10¹¹ on one node (`DIST_LOGR_DELTA` 0: logR = logn / 2): 2³¹-point planes → per APU rows 2¹³ × C 2¹⁶ = 2²⁹
points (4.29 GB); 2³⁰ → 2¹³ × 2¹⁵.

## 2. The microbenchmark: `bench/24_transpose [logq (29)] [logrows (13)] [reps (5)]`

Out of place x → y on 2^logq 8-byte points (rows × C), one APU and then four concurrently; GB/s = 16 B × points / t,
median and best of 5 after a warm-up; every transpose's y compared bit-for-bit with the production kernel's on the
device. Variants: `memcpy d2d`, uint4 copy kernel (the streaming ceilings); `t32` = the production `k_transpose`;
`t32 + copy back` (the production pair, 32 B/point); `t32 st16/32/64MB` = the same kernel with its tiles ordered in
supertiles whose source + destination is 16 / 32 / 64 MB; `t64 [st…]` = a 64 × 64 LDS tile (33 KB, block (64, 8));
`strided write` (`k_gather_mn`'s pattern) and `strided read` (the untiled forms).

Build: `make bench/24_transpose` (root Makefile; `module load rocm`). Run: `srun --jobid=$J ./bench/24_transpose 29 13 5`.

**Reading.** The production transpose already runs at the device copy rate (0.97–1.03× memcpy, 0.93–0.95× the uint4
copy kernel): a plane transpose is a pure stream with no reuse, and the 32 × 32 LDS tile turns both sides into 256 B
coalesced segments, which HBM3 serves at full rate. Ordering the tiles in 16 / 32 / 64 MB supertiles (source + destination
each in 8 KB contiguous runs) changes nothing the memory system rewards — it is 1–11 % *slower* (the row-band order's
longer contiguous source runs win over the supertile's balance of the two sides). The 64 × 64 tile (33 KB LDS, 512
threads, fewer blocks per CU) is 5–13 % slower. No variant beats the production kernel; the ≥ 10 % bar of the task is not
met in any shape, on one APU or four. The only large ratio in the table is the **untiled** strided form at 0.11–0.13× —
and that is the pattern of `k_gather` / `k_gather_mn` (coalesced read, 8-byte strided write), not of any production
transpose; see §3 for why it is not a win either.

## 3. Decision: no gain — the switch is not built

* **The microbenchmark shows no variant ≥ 10 % faster than the production kernel** (measured, §2): the best IC-sized
  variant is 0.99× `t32` on four APUs, the typical one 0.95×; on one APU 0.89–0.98×. The production transpose is at the
  copy rate, so no transpose kernel change can gain more than the 0–7 % gap to the uint4 copy kernel, and tiling
  for the Infinity Cache is not the way to close it (a transpose has no reuse to cache).
* **The share at stake is ≈ 1 %, not 16 %** (measured at 10¹⁰, modelled at 10¹¹). One 10¹⁰ run with `RNS_VERBOSE=1`
  (job 22403, s24-26, 03:46 EDT; `~/N116/e10_verbose.log`; `total` 23.51 s = bs 7.4 + 10dP 0.6 + dm 5.1 + init 8.4 +
  other 1.9; VERIFY OK): the 60 four-step products (strategy B, 2²⁰ … 2³⁰ and 3·2¹⁹ … 3·2²⁹ planes) sum to 2.03 s, of
  which their `crt` part — the four `k_transpose` + copy-back pairs **plus** the CRT and the carry scatter — is 0.249 s
  and the `load` part (the untiled gathers from the operands) 0.357 s. The transposes are therefore < 0.25 s of 13.1 s
  of computing (< 1.9 %); from the bench rates the four pairs of a 2²⁸-point-per-APU plane cost 4 × 2 × 2²⁸ × 16 B /
  3.2 TB/s ≈ 11 ms against the 32 ms `crt` of the 2³⁰ product, i.e. ≈ ⅓ of `crt` → ≈ 0.08 s ≈ 0.6 % of the run
  (modelled from the measured rates and parts). At 10¹¹ the four-step share is the same order (the planes are 2× larger,
  the run 7× longer); the 16 % of bench/13 was a different multiply (RESULTS §14).
* **Modelled delta at the target: 0 s.** The item's formula 16 % × (1 − 1/ratio) with the measured ratio ≤ 1.0 gives
  nothing; with the true share (≈ 1 %) even a hypothetical 1.3× would be ≈ −0.5 s of the 284 s.
* **The untiled gathers are the only slow transposing kernels (0.11–0.13× the tiled rate, measured), but they are not
  bandwidth-bound where they run**: `k_gather`'s `load` is 0.36 s across all 60 products, dominated by reading the
  operand through `acc_get` (host / VMM memory); the strided-write part at the bench rate is 2 × 4 × 2²⁸ × 16 B / 0.4 TB/s
  ≈ 86 ms for the 2³⁰ product against its measured `load` of 41 ms — so the write side is not what the measured time
  is (the planes are gathered before they are large enough to hurt). Tiling `k_gather` / `k_gather_mn` through LDS is
  a ≤ 0.3 s item at 10¹⁰ on one node (upper bound, modelled); at the target the general-map `redistribute` part is
  the xGMI / fabric exchange, not these kernels. Not pursued here; noted for the integrator.

**Recommendation.** Close TARGET_HW_REVIEW §3 item 5 as measured-and-rejected: the one-node transposes already run at
the HBM copy rate (3.0–3.4 TB/s per APU, 13–14 TB/s per node), the IC-sized supertile and 64 × 64 tile orders are
1–13 % slower, and the transposes are ≈ 1 % of the run, not 16 %. No `NTT_TRANSPOSE_TILE` switch; no change to
`ecalc/`. If a transpose is ever to be cut, the lever is the copy back after `k_transpose` (an equal second plane pass;
a pointer rotation of the four planes through `xt` would remove it — ≈ 0.04 s at 10¹⁰, modelled), not the cache.
